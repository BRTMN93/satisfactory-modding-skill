# SML: content registration and session settings

Part of the `satisfactory-modding` skill; config, subsystems, RCO and commands are in `references/sml-config-networking.md`. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

### Content registration [source]
- `UModContentRegistry::Get(WorldContext)`: `RegisterSchematic`, `RegisterResearchTree`, `RegisterRecipe`, `RegisterResourceSinkItemPointTable` and the `GetRegistered*` queries. Signatures: `ModContentRegistry.h:167-206`. Docs.ficsit.app confirms them.
- Warning: docs.ficsit.app calls the Mod Content Registry and the Content Tag Registry game instance subsystems. In SML 3.12 both are `UWorldSubsystem`s (`ModContentRegistry.h:161`, `ContentTagRegistry.h:42`), re-created and re-filled per world. The instance subsystems are the RCO, game map and session settings registries (`RemoteCallObjectRegistry.h:9`, `GameMapRegistry.h:73`, `SessionSettingsRegistry.h:24`). **[source]** (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- Items are not registered. They bind themselves through registered schematics and research trees. The simplest way is to put them in `mSchematics` and `mResearchTrees` on the world module.
- The registries close at the world's BeginPlay, so register in `INITIALIZATION` at the latest (the freeze message says "register in Initialization, not Post Initialization", `ModContentRegistry.cpp:123`; the log category is `LogContentRegistry`).
- **Resource sink points** are two tables on the world module: `mResourceSinkItemPointsTable` (Default track) and `mExplorationResourceSinkItemPointsTable` (Exploration track, only Alien DNA in the vanilla game) (`Module/GameWorldModule.h:36-51`, applied in `GameWorldModule.cpp:80-86`). By code: `RegisterResourceSinkItemPointTable(ModRef, Table, EResourceSinkTrack)` with `RST_Default` or `RST_Exploration`. The row struct is `FResourceSinkPointsData{ItemClass, Points, OverriddenResourceSinkPoints=-1}`; a table with another row struct is rejected with an invalid-registration notification and no crash (`ModContentRegistry.cpp:614-640`). Warning: docs.ficsit.app knows one table per world module. **[source]** (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **`mIncludeInBuilds = Never` does not keep an `FGSchematic` out of a mod's cook.** The enum default is `IIB_Never` (0); the property is editor-only and `AssetRegistrySearchable` (`FGSchematic.h:300-303`, `IncludeInBuild.h:14-21`, `FGAssetManager.h:28-37`; SML sets `PublicBuilds` in its `SessionSetting` constructor, `SessionSetting.cpp:10`). Docs say to set `PublicBuilds`; the test: two Blueprint schematics, one `IIB_Never` and one `IIB_PublicBuilds`, in a folder covered by an `FGSchematic` scan rule of the mod's GameFeatureData, were both cooked, both packages exist in the packaged game, both classes load and both are registered primary assets (`Schematic_<A> package exists=1 class loaded=1` for each; primary assets `[FGSchematic:Schematic_<A>;FGSchematic:Schematic_<B>]`). Cause (starter project): `Config/DefaultEngine.ini:316` has `;AssetManagerClassName=/Script/FactoryGame.FGAssetManager` commented out and `Source/FactoryGame/Private/FGAssetManager.cpp` is a generated stub (`GetPackageCookRule` returns an empty rule, `ModifyCook` does nothing), so the include-in-build filtering never runs for mods. A mod that wants a schematic out of the game leaves it out of its content. **[?]** Whether the schematic manager ignores a `Never` schematic at runtime was not checked (the property is editor-only data). (2026-10-24, game 513885, SML 3.12.0)
- A new building consists of a building Blueprint, a building descriptor and a recipe unlocked by a schematic. An example is in ExampleMod.
- Tags: `UContentTagRegistry` **[source]** API: `Get`, `GetGameplayTagContainerFor`, `AddGameplayTagsTo`, `RemoveGameplayTagsFrom`, `RegisterTagAdditionTable` (`ContentTagRegistry.h:49-77`); it freezes with the content registry, and the world module has `mContentTagAdditionsTable`. **[?]** Docs only: tags are not replicated (register on both sides), there is no reverse lookup (build your own cache), the tag for special item descriptors is `SML.Registry.Item.SpecialItemDescriptor`, and the vanilla `mGameplayTags` are reused. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

### Session Settings
Per-save, replicated settings, unlike a config (per install).
- Create `USMLSessionSetting` assets and list them in the instance module's `SessionSettings` array (a C++ root can add one at `CONSTRUCTION`). Tested: the setting was registered and found by `USessionSettingsManager::FindSessionSetting`; `SetValue` + `OnApply` set it; the header of the next save then carries it in the map options, next to SML's own, `?skipOnboarding?SessionSettings=<Mod>.Flag=AgAAAAQAAAABAAAA,SML.ForceAllowCheats=AgAAAAQAAAAAAAAA`, while the game mode's `OptionsString` did not change. **[source]** The values travel in the map-travel option `SessionSettings` (`SessionSettingsManager.cpp:14,88,113`). Read them with `World->GetSubsystem<USessionSettingsManager>()->GetIntOptionValue("<ModRef>.Id")` (`SessionSettingsManager.h:13`, `FGOptionInterface.h:84`). Prefix the setting id with the mod reference; docs add that a getter of the wrong type fails silently ([?]).
- **Not restored on a URL load.** Loading a save through `?loadgame=` (the `-ini` `LocalMapOptions` URL every automated test uses) finds the setting but does not apply it (`applied=False`), although the header holds it as true and the game mode's options have no `SessionSettings=` part; SML's own `SML.ForceAllowCheats` behaves the same. A test that needs one sets it in code after the load (`SetValue` + `OnApply`) or passes the CVar. Evidence: `<TAG> B15b setting found=1 applied=False options=?Name=Player?skipOnboarding?listen?loadgame=<save>` after `World Serialization (load): 0.094 seconds`. **[?]** The cause (likely that the menu's load passes the header's `?SessionSettings=` into the travel URL and the `-ini` URL does not) and whether the in-game Load menu restores them were not checked. (2026-10-24, game 513885, SML 3.12.0)
- **[source]** SML forces `ShowInBuilds`, `ManagerTypeAvailability` and `IsSettingSessionWide` on load (`SessionSetting.cpp:10-22`). Editor validation: `ApplyType` unset "would crash the game at runtime", and at least one widget entry with category and sub category is needed (`:55`).
- Docs.ficsit.app: the settings live in the save as part of the map travel URL and cannot be edited outside the game. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- Logs from Blueprints: `UBlueprintLoggingLibrary`, writes as `Log<ModRef>`.
