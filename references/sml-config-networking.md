## SML: config, subsystems, networking, commands, content, tools

### Config
- **Creating:** a Blueprint child of `UModConfiguration` with `FConfigId{ModReference, Category}`.
  - Properties: `UConfigPropertyBool`, `Float`, `Integer`, `String`, `Class`, `Array`, `Section`.
  - Flags: `bRequiresWorldReload` only restricts the UI to the menu, `bHidden`, `bAllowUserReset`.
  - **[source]** Slider in the mod's settings: use the classes `UCP_Integer` and `UCP_Float` from `Configuration/Properties/WidgetExtension/`. They have `WidgetType` (text field, slider `CPI_Slider` / `CPF_Slider`, spin box, and for integers also a list from an enum) and `MinValue` and `MaxValue`. They inherit from `UConfigPropertyInteger` and `UConfigPropertyFloat`, so reading the value from C++ does not change.
  - Registration through the `ModConfigurations` array, which happens in `INITIALIZATION`.
- **A configuration can be built entirely in C++, without an editor asset.** Make a non-abstract C++ child of `UModConfiguration` (set `ConfigId`, `DisplayName` in its constructor) and add its class to `ModConfigurations` in the game instance module's constructor. In `DispatchLifecycleEvent`, before calling `Super` in `INITIALIZATION` (SML registers the configurations there and reads the file at once), fill the class default object's `RootSection`: `NewObject` of SML's Blueprint property classes, loaded with `LoadClass<UConfigPropertySection>(nullptr, TEXT("/SML/Interface/UI/Menu/Mods/ConfigProperties/BP_ConfigPropertySection.BP_ConfigPropertySection_C"))` and likewise `BP_ConfigPropertyFloat`, `BP_ConfigPropertyBool`, with the CDO as outer **[?]** (a 2026-10-24 test: properties with the config CDO as outer never save through `MarkDirty()`, the root section must be the outer, see "Writing"; the project of this entry saved values, so its outer was probably the root section, but this was not re-read); set `DisplayName`, `Tooltip`, `DefaultValue` and `Value`, and on the `UCP_Float` children `WidgetType` (`CPF_Slider`, `CPF_Spinbox`), `MinValue`, `MaxValue`; add each to `SectionProperties` under its key. These Blueprint children are what carries the menu widget; the bare C++ property classes have none.
  - Result in the packaged game: `LogSatisfactoryModLoader: Registering configuration /Script/<Mod>.<ConfigClass>`, `LogConfigManager: Display: Successfully loaded configuration from ../../../FactoryGame/Configs/<Mod>.cfg`, and the file written with every key and its default; a value set from code through the root section and `MarkDirty()` was read back from the file after a game restart.
  - For whole numbers use `BP_ConfigPropertyInteger` (`UCP_Integer`, `CPI_Slider`). A float slider shows two decimals (a grace period of 30 s became 61.47 s after a drag).
  - In the Mods menu each property shows its `DisplayName` left and the widget right: a slider has its value in a box on the right, a spin box (`CPF_Spinbox`) its value in the middle with arrows, so mixing the two in one list looks inconsistent, and a name longer than about 30 characters runs into the widget at 1440 px width. Keep names short and put the rest in `Tooltip`.
  - Values changed in the menu are written to the file at once. SML does not clamp a loaded float to `MinValue`/`MaxValue` (they only limit the widget), so check the values read from the file.
  - Evidence: packaged-game logs of 2026-10-03 20:16 and 20:31 UTC, two screenshots of Main menu -> Mods -> `<Mod>` of the menu, the file after a slider drag (`"<Setting>": 61.466056823730469`). (2026-10-03, game 502094, SML 3.12.0)
- **Mod settings built in C++ were locked in the pause menu.** Config properties made with `NewObject<T>(Outer, LoadClass(".../BP_ConfigPropertyFloat_C" etc.))` could be changed from the main menu but did not react at all in the pause menu (sliders and bools). `UConfigProperty::bRequiresWorldReload` ("only editable from the main menu") was not set in code, so it came from the class defaults. Setting `Property->bRequiresWorldReload = false` on every property made all of them editable in a world, and the change went to the file (`Saved configuration to ../../../FactoryGame/Configs/<Mod>.cfg`). **[?]** That the Blueprint property classes default the flag to true was not read, only inferred from the fix. Also: a launch straight into a save (`GameDefaultMap` set to the save, as a test loop does) sends "Exit to Main Menu" back into that save, so the main menu cannot be reached in such a run. Evidence: the player's checks before and after the change, the config file. (2026-10-04, game 502094, SML 3.12.0)
- **File:** `<Game>\FactoryGame\Configs\<ModRef>.cfg` when `FConfigId.ConfigCategory` is empty; with a non-empty category it is `Configs\<ModRef>\<Category>.cfg` (`ConfigManager.cpp:313-320`); a missing file is written at registration (`Saved configuration to ../../../FactoryGame/Configs/<ModRef>/<Category>.cfg`). It is JSON with the field `SML_ModVersion_DoNotChange`. In the game, edit the config in Main menu → Mods → `<Mod>`. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
  - A file that fails JSON parsing is skipped with `LogConfigManager: Error: Failed to parse configuration file <path>` and the defaults are used. The file is **not** rewritten at load (still `{ broken` 12 s later); the first save, even a `MarkDirty()` without a value change, overwrites it with the defaults (198 ms after `MarkDirty`), so the user's file is lost then (`ConfigManager.cpp:91`, a `TODO` there about renaming it). **[source]** `UConfigManager::ResetToDefault(ConfigId)` resets a configuration to the defaults (`ConfigManager.cpp:194`). (2026-10-24, game 513885, SML 3.12.0)
  - On a dedicated server there is no config UI; the server reads the `FactoryGame\Configs` folder next to its own binaries. [?] docs only (faq). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **FText:** `UModConfiguration::DisplayName` and `Description`, `UConfigProperty::DisplayName` and `Tooltip` (and `ChatCommandInstance::Usage`, below) are `FText`, not `FString` (`ModConfiguration.h:39,43`, `ConfigProperty.h:26,30`). Use `NSLOCTEXT`/`LOCTEXT`; `FText::FromString` loses the localization key. **[source]** (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **Reading from C++:** right-click the config asset → "Generate C++ Config Struct Header", then `F<Asset>Struct::GetActiveConfig(WorldContext)`. If the config is not registered yet or there is no world, you get a zeroed struct. The docs name the menu entries differently: see `references/mod-structure.md` (`SMLEditor`). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **Writing:** `GetConfigurationRootSection(FConfigId)` → find the property → set `Value` → `MarkDirty()`. The change is saved 0.2 s later (199-202 ms in 7 runs, `Saved configuration to .../Configs/<ModRef>.cfg` in that frame), and the values take effect immediately. `UConfigProperty::MarkDirty()` calls `UConfigManager::MarkConfigurationDirty(ConfigId)`, which queues the config and starts a 0.2 s one-shot timer (`ConfigManager.cpp:134-150`). **[source]** A 10 s periodic timer writes what is left (`:121-131`); it was not seen, the 0.2 s timer always wrote first. The `OnPreExit` flush does not save a change that is still pending (see the exit bullet below). (2026-10-24, game 513885, SML 3.12.0)
  - **`MarkDirty()` is a silent no-op** when the properties were created with the config class default object as outer (`NewObject<UConfigPropertyInteger>(GetMutableDefault<UMyConfig>())`) and only put into `RootSection->SectionProperties`: SML copies the root section per registration, instanced subobjects are copied only when their outer is the template section, so such properties stay shared with the default and `MarkDirty` walks the outer chain without meeting the `URootConfigValueHolder` (`ConfigProperty.cpp:18-26`). Loading still works; changes are never written (not at 0.2 s, not at exit). Give the properties the root section as outer: `NewObject<UConfigPropertyInteger>(Defaults->RootSection)`. Evidence: with the default object as outer the file stayed `"Counter": 1` after exits at 0.5 s and 5 s; with the root section as outer it was written after ~200 ms. (2026-10-24, game 513885, SML 3.12.0)
- Warning: docs.ficsit.app shows other config API signatures than SML 3.12 has: `ReloadModConfigurations(bool bSaveOnSchemaChange)`, `RegisterModConfiguration(FConfigId, Class)`, a colour property and a `Mark Property Dirty` node. In 3.12 `ConfigManager.h` has `ReloadModConfigurations()` and `RegisterModConfiguration(TSubclassOf<UModConfiguration>)` (the id comes from the class default object); the property classes are Array, Bool, Class, Float, Integer, Section and String (no colour; `Configuration/Properties/`); the dirty marks are `MarkConfigurationDirty(ConfigId)` and `UConfigProperty::MarkDirty()`. **[source]** (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

- **A config value set from code persists into later game starts.** Setting a property's `Value` on the mod's configuration root and calling `MarkDirty()` writes the mod's config file; the next game start reads that value, not the default. A test that changes a setting for itself therefore leaves it for the next test and for the player: a later test that expected the default failed until it set the value itself. Evidence: two runs set an integer setting to 0 with `MarkDirty`, the next run read 0 at start (`the mod holds 0`), the same run after setting the value explicitly passed. (2026-10-12, game 502094, SML 3.12.0)

Evidence 513885: `RESULT DONE B4 B4 exit at 0.02 s after MarkDirty, file written before exit=0`, last log line `Shutting down movie player`, launcher `game process exit code: 0x000BDB2B`; exits at 0.52 s and 15.00 s: `file written before exit=1`, then `LogExit: Exiting.`. (2026-10-13, game 502094, SML 3.12.0; re-tested 2026-10-24, game 513885)

### Subsystems
- `AModSubsystem : AFGSubsystem` with the `ReplicationPolicy` field:
  - `SpawnOnServer`, `SpawnOnServer_Replicate`: everywhere except `NM_Client`,
  - `SpawnOnClient`: everywhere except a dedicated server,
  - `SpawnLocal`: everywhere.
- Override `Init()`, which fires before BeginPlay. Call `Super` in BeginPlay and EndPlay.
- Registration through `ModSubsystems` or `USubsystemActorManager::RegisterSubsystemActor`.
- Getting it: `World->GetSubsystem<USubsystemActorManager>()->GetSubsystemActor<T>()`. Returns null until the actor is created or arrives through replication.
- **[source]** The default `ReplicationPolicy` is the zero value `SpawnOnServer`, so clients get nothing; `bReplicates` is set only for `SpawnOnServer_Replicate` (`SubsystemActorManager.cpp:30-32`, `ModSubsystem.cpp:3-6`). `SpawnLocal` creates an independent actor on each side; the instances are never linked over the network (`ModSubsystem.h:18-19`, `SubsystemActorManager.cpp:49`). `RegisterSubsystemActor` rejects Abstract classes with a `checkf` (`:85-86`), so an Abstract C++ base cannot be listed in `ModSubsystems`, only its Blueprint child. `WaitForSubsystem` is a Blueprint latent node; its C++ delegate is private, so from C++ poll `GetSubsystemActor<T>()` for null. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

**Keeping a subsystem's data in the save**
- `AModSubsystem` and `AFGSubsystem` do not implement `IFGSaveInterface`. Add it yourself: `class AMySubsystem : public AModSubsystem, public IFGSaveInterface`, override `ShouldSave_Implementation() const`, and mark the fields `UPROPERTY(SaveGame)`. The interface's other native events have empty defaults in the generated header, so override only what you need.
- SML spawns the subsystem with the fixed name `<ModReference>_<ClassName>` and first looks for an actor with that name loaded from the save (`USubsystemActorManager::SpawnSubsystemActor`). The saved actor with its data is reused instead of a fresh one.
- Round-tripped exactly through three save/load cycles: `int32`, `double` (bit-exact), `FString` with non-ASCII characters and quotes, `TMap<FString, FString>`, and `TMap<FString, TObjectPtr<AActor>>` holding a train station identifier, a station building, an `AFGTrain` and block signals. After each load every reference pointed to the same live object that `AFGRailroadSubsystem` and `AFGBuildableSubsystem` return.
- Order on a save load: `PostLoadGame` fires **before** `Init()`, both in frame 0 (measured 13.058 s and 13.163 s), so the `SaveGame` fields already hold the saved values inside `Init()`. On a save without the subsystem's data, or in a new game, `PostLoadGame` is not called and `Init()` sees the defaults.
- **A `TArray` of `USTRUCT`s with `UPROPERTY(SaveGame)` fields survives save and load too:** object pointers (`TObjectPtr<AFGTrain>`, a plain actor pointer), `TSubclassOf<UFGItemDescriptor>`, numbers and strings came back after each of three loads in one process. An entry whose object is gone from the world comes back with a null pointer, so drop such entries after a load and validate every number read from the save. Evidence: `load 1 of 3 … everything written came back`, and after an object was removed in the save, `Gone from the world: … 1 …` with the entry dropped. (2026-10-04, game 502094, SML 3.12.0)
- **[?]** Removing a `SaveGame` property from a class does not break older saves (the loader skips an unknown tagged property), but an older mod version reading a newer save loses the field. Keep a `DataVersion` and treat a newer one as read-only. From a code review, not tested. (2026-10-04, game 502094, SML 3.12.0)
- **[source]** Read-only is not enough for a save of a newer mod version: when an older version of the mod loads such a save and the game autosaves, the subsystem is written again with only the properties the older class knows, because tagged property serialization drops the tags it cannot match on load. The newer version then finds its new fields empty while `DataVersion` still says "new". A way to keep forward compatibility from the first release on: reserve one `UPROPERTY(SaveGame) TArray<uint8> Extension` that the first version never reads or writes, and let later versions put data that must survive a round trip through an older version into it, with their own version number inside (`FMemoryWriter`), leaving the typed fields' meaning unchanged. Complements the entry above about `DataVersion`. From a code review of the subsystem's save fields; not tested with two mod versions. (2026-10-08, game 502094, SML 3.12.0)
- **[?]** World time starts again at 0 on every load, so a mod that measures time across loads keeps its own clock in a `SaveGame` field and adds the frame time to it. Seen indirectly: such a clock grew 2.0 → 5.6 → 9.0 → 12.9 s over three loads in one process. (2026-10-04, game 502094, SML 3.12.0)
- `PreSaveGame` fires on every save, also on saves made from code, while `ShouldSave` returns true. With `return DataVersion != 0;` an empty subsystem stays out of the save entirely (no `PreSaveGame` call). Do that in a mod players may install without using: a game saved with the mod installed then carries no trace of it.
- What a save without the mod does to this data: see "Saves" in `game-classes.md`.
- Per-player data that must survive save, load and rejoin does not belong in an RCO (an RCO is not saved). Attach a component to `AFGPlayerState` through a Blueprint Actor Mixin (registered from the C++ root's `BlueprintHooks`). Tested: both player states in the save (the local one and a saved, not connected one) got the component, outered to the player state; counters set to 4242 and 4243 were back after a save and a load. The component was a C++ `UActorComponent` with `IFGSaveInterface` (`ShouldSave` true), `IFGPlayerStateComponentInterface` and the counter as `UPROPERTY(SaveGame)`. Evidence: `<TAG> B16b player state BP_PlayerState_C_2147474609 local=0 component=Mixin_ProbePlayerData_C_ProbePlayerData outer=BP_PlayerState_C_2147474609 Counter=4242` after `World Serialization (load)`. **[source]** `CopyComponentProperties(UActorComponent* into)` and a stable component name (`FGPlayerStateComponentInterface.h`, `Patching/BlueprintHookingTypes.h:23-34`); it runs on player-state copies such as a rejoin, not on a plain load, and whether a mod needs it was not checked. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **[?]** Docs only, save quirks: `SoftObjectPtr` and `SoftClassPtr` properties are not saved by the default path (store a string in `PreSaveGame` and rebuild it in `PostLoadGame`); do not set `SkipSerialization`; `GatherDependencies` must not create cycles. The save archive is private, so there is no header evidence either way. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **Save header (on a save on disk):** the format and the mod-list check are in `references/testing.md`. SML writes it through `UFGSaveSession::SetModMetadata` at `POST_INITIALIZATION` on the authority (`SMLWorldModule.cpp:31-52`). The header says setting does not append (`FGSaveSession.h:353`), and it is true: a mod that calls `SetModMetadata` itself replaces SML's mod list. Before the call the metadata was SML's `{"Version":1,"Mods":[{"Reference":...}],"FullMapName":...}`; after `SetModMetadata("{\"<Mod>\":\"B13\"}")` and a save, the header of the new save holds only that string and 0 occurrences of `"Mods"` in its first 2000 bytes, so the list used for the missing-mods warning on load is gone from that save. **[?]** Whether SML writes its list again on the next save of a session that did not call it again was not checked. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

### Networking: client ↔ server RPC (Remote Call Object)
- `UFGRemoteCallObject` with `Within=FGPlayerController`, one per player.
- Functions: `UFUNCTION(Server, Reliable)` from client to server and `UFUNCTION(Client, Reliable)` from the server to that one client.
- Every RCO needs a dummy replicated property and `GetLifetimeReplicatedProps`.
- Registration: `RemoteCallObjects` on the instance module. Getting it: `PC->GetRemoteCallObjectOfClass<T>()`. Warning: docs.ficsit.app names `AFGPlayerController::GetRemoteCallObjectByClass` and `RegisterRemoteCallObjectOfClass`; in SML 3.12 / game 513885 they are `GetRemoteCallObjectOfClass` (`FGPlayerController.h:132`, template `:416`) and `RegisterRemoteCallObjectClass` (`FGPlayerController.h:135`, `FGGameMode.h:198`; also `RegisterCallObjectOnAllCurrentPlayers`, `:200`). **[source]** (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **[source]** Registration details: `URemoteCallObjectRegistry::RegisterRemoteCallObject` is a public UFUNCTION; the module array calls it in `INITIALIZATION`, and every game mode init registers all of them again through `AFGGameMode::RegisterRemoteCallObjectClass` (`RemoteCallObjectRegistry.cpp:10-34`, `GameInstanceModule.cpp:96-99`). SML's own RCO has a `DummyReplicatedField` (`SMLRemoteCallObject.h:48`). An RCO class can also be found by the game feature scan (`UFGRemoteCallObject::GetPrimaryAssetId`; the virtual `ShouldRegisterRemoteCallObject(const AFGGameMode*)`, `FGRemoteCallObject.h:42-44`). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **[?]** Do not use `NetMulticast` in an RCO: it exists only on the server and the owning client (`Within=FGPlayerController`, `FGRemoteCallObject.h:13`), so a multicast reaches no other client (the class constraint is read in code, the crash docs describe is not tested). Use a replicated subsystem (`SpawnOnServer_Replicate`). For logic inside an RCO, see `references/multiplayer.md`. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- The server can check whether the client has a given mod: `USMLRemoteCallObject::IsClientModInstalled` and `GetClientModVersion`.
- On a listen-server host, a `UFUNCTION(Server, Reliable)` of the local player's remote call object called from server code runs at once, inside the call: its log lines came in the same frame, before the next line of the caller. `PlayerController->GetRemoteCallObjectOfClass<T>()` returned the object about 1.5 s after the world started. Evidence: packaged-game log of 2026-10-03 20:21 UTC, frame counter `[  5]` on the call and on the server function's lines. (2026-10-03, game 502094, SML 3.12.0)
- **[source]** A server RPC parameter of type `TSubclassOf<UFGItemDescriptor>` arrives from the network as a plain `UClass*`: replication checks only that it is a class, not its base. A client can send any class, and `UFGItemDescriptor::GetForm(Class)` on a class that is not a descriptor reads the wrong CDO or trips `check`. The server-side check `Item && Item->IsChildOf(UFGItemDescriptor::StaticClass())` before any use closes it. From a code review; not tried with a modified client. (2026-10-08, game 502094, SML 3.12.0)

```cpp
UCLASS() class MYMOD_API UMyRCO : public UFGRemoteCallObject { GENERATED_BODY()
public:
    virtual void GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& Out) const override; // Super + DOREPLIFETIME(UMyRCO, bDummy)
    UFUNCTION(Server, Reliable) void ServerDo(int32 Arg);  // body in ServerDo_Implementation
    UFUNCTION(Client, Reliable) void ClientGot(int32 R);
protected: UPROPERTY(Replicated) bool bDummy = true;
};
// call: if (auto* R = PC->GetRemoteCallObjectOfClass<UMyRCO>()) R->ServerDo(1);
```

### Chat commands [source]
- Class: a subclass of `AChatCommandInstance`. In the constructor set `CommandName`, `Aliases`, `Usage`, `MinNumberOfArguments`, `bOnlyUsableByPlayer`.
- Logic: override `ExecuteCommand_Implementation(UCommandSender*, const TArray<FString>&, const FString&)`, which returns `EExecutionStatus`.
- Registration: `mChatCommands`, server only, or `AChatCommandSubsystem::Get(World)->RegisterCommand(ModRef, Class)`. Docs.ficsit.app confirms the class, the fields, `ExecuteCommand` and `mChatCommands` on the world module; `Usage` is an `FText` (`ChatCommandInstance.h:71`). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **[source]** Helpers: `EExecutionStatus` is `COMPLETED`, `UNCOMPLETED`, `INSUFFICIENT_PERMISSIONS` or `BAD_ARGUMENTS`. `AChatCommandSubsystem::ParsePlayerName` accepts `@self`/`@s`, `@all`/`@a` or an exact player name (`ChatCommandLibrary.cpp:50-72`). Fewer arguments than `MinNumberOfArguments` prints the usage and does not call the command. (2026-10-24, game 513885, SML 3.12.0)
- **[source]** `SML.cfg` (in the `Configs` folder) has two options: `disabledChatCommands` (entries `<ModRef>:<CommandName>`; it blocks player senders only and answers `INSUFFICIENT_PERMISSIONS`; docs say the host's list applies to clients) and `enableFunchookLogging` (`SMLConfiguration.cpp:11-23`, `ChatCommandLibrary.cpp:76-78,143`). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

### Console commands
- `static FAutoConsoleCommandWithWorldArgsAndOutputDevice X(TEXT("MyMod.Cmd"), TEXT("description"), FConsoleCommandWithWorldArgsAndOutputDeviceDelegate::CreateLambda(...));` works in a Shipping build. Open the console with the `~` key.
