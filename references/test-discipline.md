# Test discipline: working conventions for a series of tests

Part of the `satisfactory-modding` skill; watching runs and watchers are in `references/test-automation.md`, queues and runner agents in `references/test-queues.md`. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

**Working discipline for a series of tests** (a set of working conventions that proved useful, not game facts)
- **When the main model's quota is nearly gone, hand the whole closing to one sub-agent.** The main session wrote one self-contained brief (rules, repositories, git identity, the running queue and where its output goes, the checks for each run, the build command, the documents to update and how the previous chat recorded them, the commit messages, the final report's shape and length, "never ask the user", "do not message me before the end") and started one Opus agent in the background. The agent finished the series, built twice, found and fixed two failing runs on its own (a flag after a second load in one process, a race in a scenario between restoring the test state and switching the mod on), wrote the documents, committed and pushed both repositories, and reported in 8 lines. What helps: point it at the checkpoint file and the review report instead of restating them; say which paths the repository ignores (it could not commit the results folder because `.gitignore` excludes it, and said so). The main session answered nothing in between and used almost no tokens.
- **A chat that runs many tests, long ones or frequent ones, keeps its results in a file, not in the conversation. No key result may exist only in the chat.** Results held only in the chat get blurred or invented as the context grows, and they are lost in a compact or a handover; the earliest results are the first to go. This applies to every chat that expects more than a few runs or runs of several minutes each, not only to a series announced as long. Before the first run, create a results file outside the conversation (a folder the repository ignores is fine), write its path into the chat's first message or card so that a compact keeps it, and keep to it:
  - A `Key results` block follows the checkpoint: one line per decided item (id, PASS/FAIL, the deciding number), written when the item is decided and never removed, so the first results are still one screen away after a hundred runs. A new session or a compact reads this block first.
  - After every run, before the next one starts, append one entry per checked item: the item's id, the result (`PASS`, `FAIL`, `UNDECIDED`), the evidence copied verbatim from the log (the line itself, not a paraphrase), and the path of the saved log. A result is never written from memory; when in doubt, read the log again. The run's row in the run register (next bullet) is written at the same moment.
  - Keep a `Checkpoint` block at the top of the file, updated after every run: the run table (done and still to do), the build and variant state, the backups taken and what must be restored, and the exact next step.
  - Conclusions, the final report and folding into the skill are made from the file only, never from what the conversation remembers. After a compact or a handover the first step is to read the file back and state the run count and the key results from it, before any new run.
  - When the context passes about half of its window, finish the current run, update the checkpoint and continue in a fresh session (not a fork: a fork keeps the whole context) that starts from the file (`references/project-hygiene.md`, section 8, for the compact alternative).
  - Seen: a 21-item series reached 13 runs and about 456k tokens of context with no result written anywhere but the chat; only the raw logs existed. (2026-10-24, game 513885, SML 3.12.0)
- **One run per piece of evidence: a register of runs, compared with the plan before every series. [?]** A run is identified by its key: the scenario, the save (name and the file's hash), the arguments as passed (without output names), the build (the commit the installed package was made from, and whether the tree had uncommitted changes under the packaged paths), the game and SML versions, and the conditions (quiet machine and the machine's power mode for a frame-time run, see "Frame-time runs need a quiet machine" below; release build for a gate run). Pass criteria are not part of the key: one log can satisfy the `Passes when:` lines of several items (`references/project-hygiene.md`, section 2), and that is what makes a merge possible.
  - **The register** is one append-only table for the whole project, next to the results files (for example `runs.md` in the same ignored folder): one row per run with the key fields, the result, the items it decided and the path of the saved log. A row is the results-file entry's key, not a second record of the result: the results file keeps the evidence line, the register keeps the identity and the log path. The row is written together with the results-file entry, after the run and before the next one; a row whose log file is gone is a claim, not evidence, and is not reused. Rows are only added, never edited.
  - **The build field without a package step.** Right after a successful packaging the test script writes a small stamp file into the installed mod folder (`commit=<short sha>`, `dirty=<count of changed files under the packaged paths>` taken from `git status --porcelain -- <packaged paths>` before packaging, and `dll=<hash of the mod's main DLL>`). A run that skips packaging copies commit and dirty count from the stamp into its row, but only when the installed DLL's hash still equals the stamp's; a package installed another way (the mod manager, a manual install) then shows as build `unknown`, which is never reused, so the next run packages first. The plan comparison computes the key with the same function as the row (the run script in a check-only mode), so plan and row cannot drift apart. First use: one run of `<scenario>` on `<save>` wrote row 1 with the stamp's commit; the check of the same planned run gave `exists: 1 PASS`; after one appended comment line in a packaged source file (uncommitted) it gave `run: repeat: 1 packaged files uncommitted`; against a row of an older commit `run: repeat: 9 packaged files changed since <commit>`. A full series has not run with it yet, so the `[?]` on the bullet stays. Evidence: the register row of that run, with the stamp's commit, dirty count 0, game 517554, SML 3.12.0, result PASS and the saved log. (2026-11-07, game 517554, SML 3.12.0)
  - **Before a series,** the announced table gets a `register` column, filled for every planned run: `exists: <row>` when a current row has the same key and its saved log meets the item's `Passes when:` (pattern present, number within its limit), read now, not remembered (the result is copied from that log verbatim and the run is dropped; a chat may still mark it `run` with a one-word reason in the column, such as `repeat: statistic` or `repeat: suspected flaky`, never silently); `merge: run <n>` when another planned run has the same key (one run, every item listed on it, each with its own result line); `run` otherwise, with the reason when a row exists but is stale (`repeat: <k> packaged files changed since <commit>`).
  - **A row is current** when `git diff --stat <commit>..HEAD -- <packaged paths>` is empty, `<commit>` is an ancestor of `HEAD` (`git merge-base --is-ancestor`), the row is not dirty, and the save's hash, the versions and the arguments are the same, with the same or stricter conditions. The packaged paths are everything that goes into the mod's package (`Source/`, `Content/`, `Config/`, the `.uplugin`) plus the test module's own source; a narrower per-scenario list is a project's own choice and the risk is its own. Every other row is stale: it stays in the table as history and is never reused. After a branch merge every row whose commit is not an ancestor of the new `HEAD`, or whose diff over the packaged paths is non-empty, is stale, so the same scenario names come up again as `run`; a merge that changed no packaged file keeps the rows, which is correct. A repeat on new code is never a duplicate, because the mechanism compares builds, not names.
  - **Never merged:** the run that shows the symptom without the fix and the run after the fix (different builds, so the key already separates them; both stay in the plan); a key with both PASS and FAIL rows (unstable: no reuse, the item gets its own run); a run without the conditions of the planned one (a functional run never stands for a frame-time run; a frame-time run stands for a functional run of the same key when its log meets the criterion); a dirty-tree row with anything.
  - **The release gate** runs on the release build, so no earlier row satisfies a gate line. A planned item run whose key equals a gate run moves into the gate only when the gate runs in the same session on the same build, before its test step; a gate scheduled later never absorbs an item's run, so a FAIL is found while the item is open, not at publishing.
  - **A manual test** has its step list as the scenario. Items with the same steps get one list with every item's checks in it, and one row that names all of them.
  - **A cause hunt starts from the register,** not from a new run: the rows for the scenario and save name the saved logs; a run is planned only for what those logs lack, and that lack is the run's purpose (added log lines change packaged files, so it is a new build anyway).
  - Seen: four backlog items of one chat with the same control scenario planned as four runs; a measurement on a large save in the machine's full-power mode planned once for an item and once for the gate; a manual test with the same steps planned twice for two items; a cause hunt that planned a run while the saved logs of earlier runs already held the lines. Adopted on these four duplicates; the mechanism itself has not yet been run through a series. (2026-11-07, game 517554, SML 3.12.0)
- **Every FAIL of the closing series was the scenario, not the mod.** Twice in one series the mod was right and the scenario wrong: a flag the scenario set once per process and did not reset on the second load, and two things done in one tick (restore the test state, switch the mod on) that the next frame's cycle saw in the wrong order. Before changing mod code for a FAIL, read the scenario's own steps around the failing check first.
- **Announce a series once, then stay quiet.** Before the series starts, show one table: number, scenario, save, what the run checks, state (waiting, running, PASS, FAIL) and estimated time, with the phases of a run (packaging, game start, scenario) named once there. Nothing is said before a run, during its phases or when the game is up. After each run write at most one line: the X-of-Y counter and the result (`PASS`/`FAIL`). Between tool calls during a run write no text at all, not even a short status; waiting, polling the watchers and reading logs happen silently. Say more only for a failed run, a question, a decision that is the user's, something the user must build or do, or the end of the series, which gets the table again with measured times. Watcher reports are read by the main session and not passed on unless they show a problem. Every run, also inside a queue, has a watcher that reports its result at once, so a run that ended without a result (a closed game window) is noticed. Seen: sessions narrated every run, phase and watcher message, and the user paid for tokens and reading time without learning anything new. (2026-10-12, game 502094, SML 3.12.0)
- **A silent packaging stage is normal.** Packaging can take 5 minutes with nothing in the game log (the watcher only says that the game has not started); it is not a hang and needs no message. (2026-10-06, game 502094, SML 3.12.0)
- **Put the series table in the text that ends the turn,** after the tool calls; a table written before further tool calls was not seen by the tester. Show it again when asked. (2026-10-06, game 502094, SML 3.12.0)
- **Give each job the cheapest model that does it without rework,** not the cheapest one: a small model (Haiku 5.5; high effort for watchers) for copying builds and logs, committing with given messages, the privacy check, watching runs and the behaviour watcher; a mid-size model for building, runs with measurements and folding findings; the main model for experiment design, hook code, analysis and conclusions. Seen: a small model wrote commit messages with a byte-order mark although told not to, and folding by a fresh mid-size agent took 9–13 minutes because it read the whole skill again. (2026-10-03, game 502094, SML 3.12.0)
- **Frame-time runs need a quiet machine, and a repository-searching or reviewing sub-agent counts as load.** In one series a code-review sub-agent ran during a frame-time run and the run's longest frames rose to 1.0–1.7 ms with half the thread CPU time, so the run was void; in a later series, with only light log-watcher agents running, single frames of 1.0–3.4 ms still appeared whose thread CPU time was 0.14–0.53 ms (the system pausing the game's thread). The convention that follows: no build, no packaging and no sub-agent that reads or searches the code base while a run with a frame-time limit is going; reviews and audits are scheduled before or after such a queue, and long frames are judged by the thread CPU time (`QueryThreadCycleTime`, `references/patterns-and-pitfalls.md` item 38) before they are called slow code. Evidence: log lines of the mod's frame check, e.g. `a frame of the mod's own work over 1 ms: 3.379 ms of 3.379 ms … thread CPU time of the frame 0.142 ms`, and a run voided for a parallel review sub-agent with frames 1.0–1.7 ms at about half the CPU time. (2026-11-05, game 517554, SML 3.12.0)
