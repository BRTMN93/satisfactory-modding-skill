# Test environment: headless runs, fixed step, window size, saves and cheats

Part of the `satisfactory-modding` skill. Markers: no marker = verified in practice, **[source]** = read from SML, game or engine code, not tested, **[?]** = uncertain. Split out of `references/testing.md`; the test rules, launching into a save, test mode and the pre-release checklist stay there.

- **`-DisablePlugins=A,B` starts the game without the named mods and leaves their files alone.** The engine reads the parameter in Shipping builds too (`FPluginManager::ConfigureEnabledPlugins`, `<UE-CSS>/Engine/Source/Runtime/Projects/Private/PluginManager.cpp`). The log then says `LogPluginManager: Display: Skipping loading modules for <Mod>. Plugin is not enabled for current target.` and SML's list of loaded mods (`LogSatisfactoryModLoader: Display: <Mod>: <version>`) leaves the mod out. A test script can pass every `*.uplugin` name found under `FactoryGame\Mods` except SML and the mod under test, so a test run is not disturbed by whatever else is installed. Saves that were edited with two other mods installed loaded without them. (2026-10-03, game 502094, SML 3.12.0)
- **A small window cuts the GPU load of automated test runs by a third; the game stores the window arguments in the user's settings.**
  - `-windowed -ResX=640 -ResY=480` gives a window of 960×720 real pixels at 150 % display scaling. During the same train scenario the GPU board power fell from 43.4 W to 33.9 W on average (idle desktop 16–17 W, so about a third less above idle) and from 55 W to 40 W at the peak. The game's CPU use (2 cores) and frame rate (59 fps, capped at 60) did not change, and the scenario's result lines were the same.
  - Setting the scalability groups to 0 on top of the small window changed nothing measurable; the tester's settings already had most groups at 0.
  - The game rewrites `%LOCALAPPDATA%\FactoryGame\Saved\Config\Windows\GameUserSettings.ini` on every start. A run with `-ResX`/`-ResY` stored the test window there (`ResolutionSizeX/Y`, `LastUserConfirmedResolutionSizeX/Y`, `LastConfirmedFullscreenMode`), so the user's next normal start would have opened in the test window. Copy the file before the run and put it back after the game has closed; with that the file's SHA256 was the same before and after.
  - Quality values are stored twice in that file: in `[ScalabilityGroups]` and inside the `mIntValues=(("sg.…Quality", N),…)` line of `[/Script/FactoryGame.FGGameUserSettings]`. Values edited in both places before the start were kept by the game, except `sg.GlobalIlluminationQuality`, which it put back to 1.
  - (2026-10-03, game 502094, SML 3.12.0)
- **Measuring the GPU load of a run:** sample `nvidia-smi --query-gpu=utilization.gpu,power.draw,temperature.gpu --format=csv,noheader,nounits` every 5 s while the game process exists, together with the game process's CPU seconds and working set; judge only the scenario part (from its first line to its result line) and take the idle value from the samples before the game started. 5 s samples miss short peaks (loading reached 100 % and 119 W between them). Evidence: the 43.4 W and 33.9 W averages above were measured this way. (2026-10-03, game 502094, SML 3.12.0)
- **An unpatched game client cannot run without a renderer.** Started with `-nullrhi`, with only SML and the tested mod loaded, the packaged client loaded a save, ran the mod's first tick and died about 10 s later: `EXCEPTION_ACCESS_VIOLATION reading address 0x00000000000002e0` in the game's own `UFGTextRenderer::TickComponent` (`FGTextRenderer.cpp:54`) calling `UCanvas::K2_DrawText`. The frame counter moved only from 54 to 64 in those 10 s. So an unpatched client under `-nullrhi` is no test target; skipping the text renderer tick changes that (next bullet). A dedicated server is the other renderer-free target (measured in the bullets below). **[?]** The SML 3.12 guide in the docs says the engine no longer loads mesh data under `-nullrhi` (a server memory optimisation), which fits a client that dies in its first frames. A windowless but rendering alternative is `-RenderOffScreen`, which ran a client cleanly (`references/testing-launch.md`). A mod's own GPU code can also crash a client started with `-nullrhi`: see "A render target (any texture) has no resource when the game cannot render" in `domains/rendering/render-targets.md`. (2026-10-03, game 502094, SML 3.12.0)
- **The game client runs without a renderer when the game's text renderer tick is skipped.** `-nullrhi` still kills the packaged client about 7 s after `LoadMap` (`EXCEPTION_ACCESS_VIOLATION reading address 0x00000000000002e0`, `UCanvas::K2_DrawText` ← `UFGTextRenderer::TickComponent`, no mod frame), so the earlier statement that the client cannot run without a renderer holds only for an unpatched client. One SML hook that cancels that tick when `FApp::CanEverRender()` is false is enough: `UFGTextRenderer::TickComponent` is private in the header, so hook the public base declaration with the class's default object, `SUBSCRIBE_METHOD_VIRTUAL(UActorComponent::TickComponent, GetMutableDefault<UFGTextRenderer>(), [](auto& Scope, UActorComponent* Self, float, ELevelTick, FActorComponentTickFunction*) { if (!FApp::CanEverRender()) Scope.Cancel(); })`; it compiles and hooks the override body. Evidence: 3 of 3 runs of 600 game s each with only SML and the probe mod, no crash, exit code 0, about 244 skipped text renderer ticks per game second on a small save. Measured on a small save (means after the first 90 s, samples every 2 s): window 640×480 lowest settings CPU 10.2 % of all cores, GPU 3D 26 %, VRAM 1.45 GB, RAM 4.3 GB, process start to world 15.3 s; `-nullrhi` + hook CPU 1.7 %, GPU 0, VRAM 0, RAM 1.8 GB, 5.7 s; dedicated server CPU 0.6 %, RAM 2.9 GB. The client still honours the user's `t.MaxFPS` from `GameUserSettings.ini` under `-nullrhi` (60 ticks per s with `t.MaxFPS 60`). (2026-11-15, game 517554, SML 3.12.0)
- **A mod that builds a `UStaticMesh` at runtime kills a `-nullrhi` client even with the text renderer hook.** Two packaged runs with the `UFGTextRenderer` tick skipped died in the first seconds of their scenario at the same check: `Assertion failed: FApp::CanEverRender() || !FPlatformProperties::RequiresCookedData() [StaticMesh.cpp:2694] RenderData should not initialize resources in headless cooked runs`, stack `FStaticMeshRenderData::InitResources` ← `UStaticMesh::InitResources` ← `UStaticMesh::BuildFromMeshDescriptions` ← the mod's mesh builder. **[source]** `BuildFromMeshDescriptions` calls `InitResources()` at its end unconditionally (`StaticMesh.cpp:8367` onwards), and the check is a `checkf`, live in the game's Shipping build. So a mod runs without a renderer only when it skips runtime mesh building while `!FApp::CanEverRender()`. **[?]** A test-only workaround that cancels `UStaticMesh::BuildFromMeshDescriptions` (exported `ENGINE_API`, so an SML hook should reach it) when the game cannot render is untried. (2026-11-15, game 517554, SML 3.12.0)
- **`-UseFixedTimeStep` works in the packaged (Shipping) game, client and dedicated server, with a fixed step of 1/30 s.** Every frame advances game time by exactly 1/30 s and frames run back to back, so game time runs as fast as the machine allows. Measured speeds (game s per wall s, small save): `-nullrhi` client with the text renderer hook 26–31×, dedicated server 8.1×, window 640×480 7.4–7.8×. **[source]** `TargetRules.bWithFixedTimeStepSupport` defaults to true for every configuration (`TargetRules.cs:1540`, `UEBuildTarget.cs:5749`), so `WITH_FIXED_TIME_STEP_SUPPORT` is 1 in Shipping. `-FPS=<n>` and `-benchmark` are parsed only outside Shipping (`LaunchEngineLoop.cpp:4462-4476`, `:2284-2289`): `-UseFixedTimeStep -FPS=60` still stepped 1/30 (3600 of 3600 ticks), `-benchmark -FPS=30` changed nothing. `NetServerMaxTickRate` makes no difference under a fixed step. For another step or a real-time pace a mod installs a `UEngineCustomTimeStep` with `GEngine->SetCustomTimeStep()` whose `UpdateTimeStep` calls `FApp::UpdateLastTime()`, sets `FApp::SetDeltaTime(Step)` and `FApp::SetCurrentTime(FApp::GetCurrentTime() + Step)` (sleeping to the wall clock for a real-time pace) and returns false; that gave 1/30 on 9000 of 9000 ticks on client and server. (2026-11-15, game 517554, SML 3.12.0, UE 5.6.1-CSS)
- **A fixed step is deterministic across environments and pace; the step size is not neutral.** With a 1/30 fixed step the per-second state of a small save (train position and speed, docking state, item counts per container, platform and wagon) was identical over 600 game s in a 640×480 window, in a `-nullrhi` client, on a dedicated server, at real-time pace and at 28× (same md5 of the state lines, 9 of 10 runs; one `-nullrhi` run differed slightly from 120 s on, not explained **[?]**). Without a fixed step (1/60 at `t.MaxFPS 60`) and with `TimeDilation 4` (the same as `slomo 4`) the results differ from the 1/30 runs (train x at 300 s 292886–292997 and 289939 against 291703; container items 1003–1057 against 1046). So an accelerated run stands for players at the same step (1/30 for 30 FPS); it does not reproduce a 60 FPS game, and `TimeDilation` is not an honest accelerator. (2026-11-15, game 517554, SML 3.12.0)
- **A fixed 1/60 s game step from a helper mod's `UEngineCustomTimeStep` reproduces normal 60 FPS test runs, at about 3–4× speed in a small window.** `-UseFixedTimeStep` gives only 1/30 s in Shipping, which changes per-frame budgets and frame-counted arguments of a mod built for 60 FPS. A test-only helper mod sets its own step instead: a `UEngineCustomTimeStep` subclass whose `UpdateTimeStep` calls `FApp::UpdateLastTime()`, `FApp::SetDeltaTime(1.0/60)`, `FApp::SetCurrentTime(FApp::GetCurrentTime() + 1.0/60)` and returns false (the engine then skips its own time update and frame limit), `GetSynchronizationState()` returns `Synchronized`, set with `GEngine->SetCustomTimeStep(...)` in `FCoreDelegates::OnPostEngineInit` (it returned true). Two scenarios of a train mod (<scenario A>, <scenario B>), each compared with a normal run of the same build, save and arguments at 59–60 FPS: every check line the same and passed, no mod warning; numbers equal or one frame apart (`t=228.7` against `228.8`, a leg 24.2 s against 24.3 s), and in the second scenario a hand-stop position of 227 m against 223–235 m over four normal runs (event times there 2 s later than any normal run). Speed (game s per wall s from the scenario start, 640×480 window, all `sg.*Quality` 0): ×2.8–3.0 with the laptop in its normal power mode, ×3.2–3.7 in turbo; the same game thread runs slower without turbo, so speed-up figures need the power mode next to them. **[?]** Under `-nullrhi` the same helper should be about 4× faster again (the ratio of the `-nullrhi` and window speeds measured at 1/30 s), but not for a mod that builds a `UStaticMesh` at runtime (entry above in this file). **[?]** Bit-for-bit equality with a normal run is not expected: the normal run's own step varies frame to frame. (2026-11-15, game 517554, SML 3.12.0, Windows 11 laptop)
- **VSync holds a helper mod's fixed-step acceleration at x1.** With UseVSync=True / ("r.VSync", 1) in GameUserSettings.ini the frames wait for the display (60 Hz), so a fixed 1/60 s step gives game time at exactly wall time (measured x1.3 including load, game 30 s per wall 30 s); with VSync switched off for the run the same machine and scenario reached x3.1. VSync is switched off in the copy of the settings the test run uses, and the player's file is restored afterwards. Evidence: game CL 520140, laptop in turbo, 2026-11-19.
- **A fixed-step run is one more sample of the frame sequence, not a copy of a normal run; a pass condition that hangs on arrival order can flip.** A mod's scenario where two trains wait at platforms (pass condition: room at docking) passed at normal speed (waits starting at 385.5/418.5 and 487.5/517.5 game s; an earlier normal run 386.5/419.5 and 488.5/518.5) and failed with a fixed 1/60 step and frames back to back in a window (waits from 390.5/473.5, "2 of 2 waits not so"); three variants of the scenario with another traffic setting passed under the same step, and 48 of 51 runs of a queue matched their normal-speed result. The normal runs already differ from each other by about 1 game s, because a normal frame's `DeltaSeconds` jitters around 1/60 while the fixed step is exact. **[?]** The divergence comes from that dt difference, not from something in the game running on the wall clock: at a fixed 1/30 step, state lines of a small save were identical at real-time pace and at 28× ("A fixed step is deterministic" above), which an accelerated wall-clock component would have broken; the order-sensitive scenario itself was not re-run at real-time pace. So an accelerated run stands for a normal one only for checks that tolerate the run-to-run spread of normal runs; a new scenario, or new arguments that change traffic control, is compared once against a normal run before its accelerated result counts. (2026-11-16, game 517554, SML 3.12.0)
- **The autosave timer follows game time, and the console variable does not set it.** With `-UseFixedTimeStep` at about 27× and the save session's interval set to 300 s, the game wrote an autosave every 9–10 wall s (about 270–300 game s). `-ExecCmds="FG.AutosaveInterval 300"` logged `FG.AutosaveInterval = "300"` but no autosave came in 15000 game s; `UFGSaveSession::SetAutoSaveEnabled(true)` plus `SetAutosaveInterval(300)` from a mod did set it. Autosave file names come from the session name in the loaded save's header, not from `AFGGameState::SetSessionName`, so a test on a copy of a save that turns autosave on overwrites the original's `<session>_autosave_0..2.sav` slots in the save folder. Evidence: three autosaves 9–10 s apart at the end of a 544.8 wall s run, named after the copied save's session. (2026-11-15, game 517554, SML 3.12.0)
- **The dedicated server's frame step is about 47 ms, not 33 ms, at its default 30 Hz limit.** Run without a tick rate setting: 21.4 ticks per game s, `DeltaSeconds` median 0.04665 (p1 0.03991, p99 0.04848). **[?]** It is three Windows timer periods (3 × 15.625 ms): the dedicated-server wait in `UnrealEngine.cpp` (`FPlatformProcess::SleepNoStats`) rounds up to the timer resolution (inferred from the numbers and the source). (2026-11-15, game 517554, SML 3.12.0, Windows 11)
- **[source]** Time sources under a custom or fixed step: `UWorld::GetRealTimeSeconds()` is the sum of undilated frame deltas (`LevelTick.cpp:1345`), not a wall clock, so under a fixed step it equals game time (confirmed by the logged values); the core ticker (`FTSTicker`) is ticked with `FApp::GetDeltaTime()` (`LaunchEngineLoop.cpp:5852`) and `FTimerManager` has no real-time mode, so both follow game time. Only `FPlatformTime::Seconds()`, `FDateTime::Now()` and file times give wall time; a mod's timeouts measured with them see fewer wall seconds per game second in an accelerated run. SML's config flush timers (`ConfigManager.cpp:131`, `:140`) follow game time. (2026-11-15, UE 5.6.1-CSS, SML 3.12.0)
- **A game that hangs on exit can stay in the process list and keep its files locked until it is ended from Task Manager.** After an automated run the game logged `LogExit: Preparing to exit.` and `Shutting down movie player`, then hung. `taskkill /F` answered "There is no running instance of the task", `Stop-Process -Force` returned without error, `Get-Process` showed it with `HasExited = True` and 4 GB of memory, and it still held `FactoryGame.log` open, so a new run could not rename the log. It did not go away in minutes. A test script should count only processes with `HasExited = false` as a running game.
  - A second hang (same log tail) again ignored `taskkill /F` ("no running instance") and `Stop-Process -Id <pid> -Force`, and it held the mod's DLLs and `.utoc`/`.ucas` locked (`cp`: "Device or resource busy"), so a new build could not be installed. Ending it from Windows Task Manager worked, where it was listed under a different name ("FactoryGame Studio"); after that `tasklist` showed no game, the files were free and the next run packaged and installed normally. So: ask the user to end the game in Task Manager (look for a FactoryGame entry), and restart Windows only if that fails too. **[?]** Why Task Manager succeeds where `taskkill /F` and `Stop-Process -Force` fail. (2026-10-04 and 2026-10-05, game 502094, SML 3.12.0, Windows 11)

- **`FParse::Value` into an `FString` stops at a comma unless told not to.** `FParse::Value(FCommandLine::Get(), TEXT("MyArg="), Out)` with `-MyArg=1,2,3` gives `1`; with `bShouldStopOnSeparator = false` (`FParse::Value(..., Out, false)`) it gives `1,2,3`. Evidence: a test's shape parameter of five numbers was read as one until the flag was set. (2026-10-23, UE 5.6.1-CSS)
  - Seen again: `-<Mod>Cut=72,2246` read with `FParse::Value(FCommandLine::Get(), TEXT("<Mod>Cut="), Text)` gave `72` and a test run on <scenario> parted a joint at X 261 Y 338 instead of X 72 Y 2246; with `false` as the fourth argument it parted at X 69 Y 2246. List values (coordinates, names) read with `false` are split by the caller. (2026-11-12, game 517554, SML 3.12.0)
- **A large save loaded without the mods it was made with looks hung on the loading screen.** Each object of a missing mod's class costs about 85 ms while loading (`LogUObjectGlobals: Warning: Failed to find object '...PersistentLevel.<Mod>_<Class>_<n>'`, several lines per object, plus `LogSave: Warning: Got object [...] of deleted class [...]`), so a save with thousands of them stays minutes on the loading screen while the log keeps growing. A test run on the player's own modded save must load the player's mods (the same save loaded in 15 s with them, and was still loading after 4 min and 2700 such lines without them). A log that still grows tells a slow load from a hang. (2026-10-23, game CL 513885, SML 3.12.0)
- A `loadgame=` option for a save that does not exist starts a **new** world, silently: no `World Serialization (load)` line, no error or warning naming the save, and the game mode's options still carry the name (`?Name=Player?skipOnboarding?listen?loadgame=<missing>`, exit code 0). A test that loads a save by name must check that the load happened, or it runs on a fresh world: the line `LogGame: World Serialization (load): 0.132 seconds` must exist. It carries no save name; the name is only in the `LoadMap:`/`Browse:` line, which a missing save has too. **[?]** The docs also say a save from a newer game version falls back to a new world; a copy of a good save with only the header changed to SaveVersion 160 and build 999999 loaded through `?loadgame=` with no version warning, so a header alone does not make a save unloadable on that path; a save really written by a newer game was not available, so the docs' claim is unproven. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **A save's header names the mods it was made with, and a test save can be checked before a run.** The header starts with uncompressed JSON, `{"Version":1,"Mods":[{"Reference","Name","Version"}],"FullMapName":"…"}`; the first ~300 bytes of the `.sav` file show it. Evidence: the header of a test save read on disk. **[source]** SML writes it at `POST_INITIALIZATION` on the authority (`SML/Private/…/SMLWorldModule.cpp:31-52`); a mod that calls `SetModMetadata` replaces SML's list (tested, `references/sml-config-networking.md`, "Save header"). On load SML warns only about a mod that is missing and about a loaded mod older than the saved one (`SaveMetadataPatch.cpp:147-156`); the console variable `SML.SkipModCompatibilityCheck` skips the check and defaults to 1 in the editor (`:14-19`). A save loaded without the mods in its header: see the slow load above. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
