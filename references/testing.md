# Testing and the pre-release checklist

Part of the `satisfactory-modding` skill. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

Watching automated runs, series and sub-agents: `references/test-automation.md`. Publishing and other people's mods: `references/publishing.md`.

**Rules**
- Test in the packaged game (rule 1 in `SKILL.md`).
- **Back up the saves before testing.** A copied save keeps its session name, so autosaves during testing overwrite the rotating slots of the *original* session. Rename the test session or turn autosave off (console variable `FG.AutosaveInterval = 0`).
- Launch parameters that change the resolution stay in the game's screen settings (`GameUserSettings.ini`), so the next normal start would open in the test window. Copy the file before the test and put it back after the game has closed (details under "Launching the game for tests"; `-Multiprocess` left the file byte-identical in a test, see `references/testing-launch.md`).
- When measuring performance, record the conditions. Fullscreen and a borderless window give different results, and with frame generation the engine's frame times are not the same as the displayed frames.
- **[?]** Do not cap the frame rate or speed up game time in timing tests: the simulation step follows the frame time (17 ms at 60 fps, 33 ms at 30), so braking distances and stop positions measured at one frame rate are not comparable with another. Reasoned, not measured. (2026-10-03, game 502094, SML 3.12.0)
- **`t.MaxFPS` set from code caps the packaged game's frame rate.** Setting the console variable `t.MaxFPS` to 30 through `IConsoleManager::Get().FindConsoleVariable(TEXT("t.MaxFPS"))->Set(...)` at the start of a test run held the game at 30.0 frames a second (133 samples of 30 s over 70 minutes, including three in-process reloads of a save). This keeps long test runs light on a weak machine. (2026-10-07, game 502094, SML 3.12.0)
- Manual tests: numbered steps, with a log-watching script confirming each step. Before saving the game, wait until the background work finishes.
- **A UI test that calls the handler directly does not prove the control works.** A scenario that closed a popup through its confirm function passed, while the player's click on the same OK button did nothing. Press the real widget (broadcast its `OnClicked`) or check that it is enabled and visible. Evidence: the scenario's PASS, then the failed click in a manual test the same day. (2026-10-04, game 502094, SML 3.12.0)
- **A manual test waits for the tester's last step before it ends.** A test that closed the game as soon as it saw its two expected events ended while the tester was still doing the final step, which looked like a crash and lost that step. Hold the game open for a while after the last expected event, or until the tester's final action, and show the current step on screen. (2026-10-05, game 502094, SML 3.12.0)
- Automation: a separate test mod enabled by a launch parameter (e.g. `-MyModTestBridge`) reads commands from a file (`commands.jsonl`), loads saves, builds and dismantles buildings, samples frame times and memory, and writes the results to files.
- Check rendering changes by comparing images pixel by pixel (old and new build, same save).

- **A test save built under another mod profile loses buildables when it is re-saved without those mods.** Track pieces and a conveyor lift were missing after a save was loaded and saved again in a profile with only SML. The save's session settings still carried the other profile's mod settings (`SessionSettings=...InfiniteZoop.BlueprintZoop=...` in `LogGameMode: ProcessServerTravel`). Build and change test saves only in the test profile, and after every change check them in the game, for example with one full lap of a test train. (2026-10-02, game 502094, SML 3.12.0)

**Launching the game for tests**
- **Starting the game straight into a save works** (docs.ficsit.app, Development → Testing). Launch `<Game>\FactoryGameSteam.exe` with:
  `-ini:Engine:[/Script/EngineSettings.GameMapsSettings]:GameDefaultMap=/Game/FactoryGame/Map/GameLevel01/Persistent_Level.Persistent_Level,[/Script/EngineSettings.GameMapsSettings]:LocalMapOptions=?skipOnboarding?listen?loadgame=<save name without path and extension>`
  - The argument has no spaces, so `Start-Process -ArgumentList @(...)` passes it unquoted.
  - The Steam client must be running.
  - **The Steam copy also needs `<Game>\Engine\Binaries\Win64\steam_appid.txt` containing `526870`.** Without it the log shows `LogSteamShared: Warning: SteamAPI failed to initialize, conditions not met.` and `LogOnlineServices: Game restarting within Steam client, exiting`. Steam then starts a second copy with only `-NO_EOS_OVERLAY`. That copy writes `FactoryGame_2.log`, because the first copy still holds the log. All your arguments are lost and the game sits in the main menu.
  - The root `FactoryGameSteam.exe` is a stub that stays alive next to `FactoryGameSteam-Win64-Shipping`.
  - On a 180 KB save it took 16–20 s from `Start-Process` to the world's BeginPlay.
  - Evidence: `LogInit: Command Line:` shows the arguments, then `LogGame: World Serialization (load)`.
  - **The local player does not get the character stored in the save.** It spawns somewhere else, and the stored character stays in the world as an idle pawn named "player". This was seen in the packaged game. It is harmless for scenarios that do not need the player. Do not save the game from such a session, though, or the save gains a second player. **[?]** The cause has not been checked. The likely one is a different player identity than in a normal Steam start.
  - **The new player starts with empty player rules, so the advanced game setting "flight" is off** even when the saved player had it. Flight is a per-player rule (`FPlayerRules::FlightMode` in `FGPlayerState.h`). Calling `AFGPlayerState::SetFlightMode(true)` on the local player's state, once `UFGBlueprintFunctionLibrary::GetLocalPlayerController(World)->GetPawn()` exists, changed `GetPlayerRules().FlightMode` from 0 to 1 about one second after the world started. The character could then fly in the packaged game.
  - **Placing the player next to the object under test.** In test mode, once the pawn exists and flight is on, `Controller->SetControlRotation(Rotation)` and then `Controller->GetPawn()->TeleportTo(Location, Rotation)` put the character in the air beside the building under test, so the tester does not have to look for the scene. Evidence: the log line `player moved next to <station A>: 1`. (2026-10-05, game 502094, SML 3.12.0)
  - **[?]** Once, after such a move, the game's "Welcome back" banner stayed on screen; the next run did not show it. Not reproduced. (2026-10-05, game 502094, SML 3.12.0)
  - The loaded save's name can be read back with `FParse::Value(FCommandLine::Get(), TEXT("loadgame="), Name)`. The value stops at the space before the next argument. Useful for a test that saves again under the same name.
  - **[?]** Leaving such a session through the menu loaded the same save again (`LoadMap: ...?closed?skipOnboarding?listen?loadgame=<save>` right after the player saved and left). The likely cause is that the `-ini` override of `LocalMapOptions` also applies to the map the menu goes back to. Seen once.
- **A developer test mode behind a custom launch parameter works in Shipping.**
  - `FParse::Value(FCommandLine::Get(), TEXT("MyModTest="), Name)` reads `-MyModTest=<Name>`.
  - Start the scenario on the next tick after the world module's `POST_INITIALIZATION`.
  - Write steps and the result to the log under a fixed tag.
  - Close the game afterwards with `GLog->Flush()` and then `FPlatformMisc::RequestExit(false, TEXT("<call site>"))`. This logs `FPlatformMisc::RequestExit(0, <call site>)` and `Engine exit requested`, then shuts down cleanly (`LogExit: Exiting.`) in about 7 s.
  - A script that reads the log should move the old `FactoryGame.log` aside itself before the launch, so no line from an earlier run is mistaken for a result.
  - **[?]** For a few seconds after its window has closed the game still holds `FactoryGame.log`; a queue script that moved the log right away failed on `Move-Item` and stopped. Wait until the file can be opened for writing. Seen once. (2026-10-05, game 502094, SML 3.12.0)
  - One cycle from launch to result took 22–24 s without packaging and 48–71 s with incremental packaging of an unchanged mod.
  - Scenarios that wait for the game, such as a train run, can end later from a timer or a delegate.
- **A scenario sets up in the loaded save everything code can set** (vehicle positions, timetables and autopilot, switches, the mod's own flags, stock) and fails on its own limit if the setup did not take; the build list for the tester holds only what code cannot do (tracks, signals, buildings, belts, machines). Evidence: a run stood for 21 minutes because one vehicle in the save had been switched out of the mod's control; the scenario now sets that flag itself. (2026-10-06, game 502094, SML 3.12.0)
- **Stock set from test code reads as a burst of flow.** Setting a station platform's inventory from a test (e.g. emptying or filling it) is seen by a rate measurement over a time window as a huge inflow or outflow (one jump read as 1821 items a minute against a real 180), and a planning pass in the same frame still plans on the readings from before the change. Pause the mod's planning a moment before the change and resume it a few seconds after; give rate checks a window that starts after the change. (2026-10-07, game 502094, SML 3.12.0)
- **A test that teleports the player to watch something must also put the character into flying movement.** Turning flight on in the player rules (`SetFlightMode(true)`) only allows flight: a character teleported into the air with `TeleportTo` fell onto the foundations below, and a series of screenshots showed the floor instead of the scene. After `TeleportTo`, `Cast<ACharacter>(Pawn)->GetCharacterMovement()->SetMovementMode(MOVE_Flying)` kept it at the spot for the whole run (29 screenshots with the scene in view). Side effect: with the character in `MOVE_Flying`, a station window opened from code with `AFGHUD::OpenInteractUI` was gone from the interact widget stack 1.5 s later (two runs in a row, 640×480), while the same scenario without the flying mode, and an older build, showed it; so set the flying mode only for a pure watch, not where the test opens windows. **[?]** Which check closes the window (movement mode or something it causes) is not known. Evidence: two test runs of 2026-10-12, the first with every screenshot of a foundation floor, the second with the platform and its crane. (2026-10-12, game 502094, SML 3.12.0)
- **A test run that changes the mod's own settings must put them back even when it ends early.** Scenarios set values through the mod's config (SML `UModConfiguration` saved to `<Game>\FactoryGame\Configs\<Mod>.cfg`) and restored "the value found at the start"; one run that ended without restoring left a settling time of 5 s instead of 120 s in the file, every later scenario read 5 as "the value found" and kept it, and an unrelated measurement scenario failed (209.6/min measured against 180/min) hours later. The fix that holds: the test launcher copies `<Mod>.cfg` before the game starts and moves the copy back after the game has closed, like `GameUserSettings.ini`. Evidence: the config file read `"SettleSec": 5` after a series; the same measurement passed at 180.3/min in an earlier series. (2026-10-13, game 502094, SML 3.12.0)
- Three loads of a save in one game process, with a return to the real main menu in between, work from test code while the game was started with the `-ini` override of `GameDefaultMap`/`LocalMapOptions`: `UGameplayStatics::OpenLevel(World, FName(TEXT("/Game/FactoryGame/Map/MenuScenes/Map_Menu_1_02")))` goes to the menu (`LogLoad: LoadMap: /Game/FactoryGame/Map/MenuScenes/Map_Menu_1_02`), and `UGameplayStatics::OpenLevel(MenuWorld, FName(TEXT("/Game/FactoryGame/Map/GameLevel01/Persistent_Level")), true, TEXT("skipOnboarding?listen?loadgame=<save>"))` loads the save again. Drive it from the core ticker (`FTSTicker`), which survives the world changes, and wait about 3 s in each new world. A `CollectGarbage` called from that ticker in the menu ran without trouble, so a test can count the mod's objects still alive after each world. Errors the game itself logs on every such load (navmesh bounds, session widgets in the menu) are not the mod's. Evidence: packaged-game log of 2026-10-03 20:24 UTC. (2026-10-03, game 502094, SML 3.12.0)
- **Saving, going to the main menu and loading the save again works in one process from a test.** `UFGSaveSession::SaveGame(<name>, callback)`, then travel to the menu map and `?loadgame=<name>` on the game map, ran four times in a row in one game process with the mod's state restored each time; driven by an `FTSTicker` that outlives the worlds. **[?]** The game process then crashed on exit after the test's result (`EXCEPTION_ACCESS_VIOLATION` with only SML frames on the stack, during `RequestExit`). (2026-10-07, game 502094, SML 3.12.0)
- A test that waits on the core ticker (`FTSTicker::GetCoreTicker()`, the way to survive world changes) must count game frames, not only wall-clock seconds. After a save had loaded, the world had begun play and the player's `UFGGameUI` existed, yet the game sat in one frame for 17 s (frame number 35 → 36 in the log brackets while the ticker kept running); `AFGHUD::OpenInteractUI` called then left no window on the interact stack 1.5 s later. Waiting until both the seconds and at least 10 frames (`GFrameCounter`) have passed fixed it, and the same windows opened every time in three loads in one process. Evidence: `<TEST_TAG> step FAILED …: window open: None` at frame 36, then PASS with 186 checks after the change. (2026-10-03, game 502094, SML 3.12.0)
- A logic module that only compares game objects through weak-pointer handles can be self-tested in the packaged game without any game object: `NewObject<UObjectRedirector>(GetTransientPackage())` gives a real, distinct `UObject` per call (the class is exported from CoreUObject and concrete, `UObject` itself is abstract), so the test module needs only `Core` and `CoreUObject`. The objects are unreferenced, so keep the whole test inside one tick. Evidence: a self-test of 84 checks built this way passed in a Shipping build, started by a launch parameter after the world loaded. (2026-10-03, game 502094, SML 3.12.0, UE 5.6.1-CSS)
- **`-DisablePlugins=A,B` starts the game without the named mods and leaves their files alone.** The engine reads the parameter in Shipping builds too (`FPluginManager::ConfigureEnabledPlugins`, `<UE-CSS>/Engine/Source/Runtime/Projects/Private/PluginManager.cpp`). The log then says `LogPluginManager: Display: Skipping loading modules for <Mod>. Plugin is not enabled for current target.` and SML's list of loaded mods (`LogSatisfactoryModLoader: Display: <Mod>: <version>`) leaves the mod out. A test script can pass every `*.uplugin` name found under `FactoryGame\Mods` except SML and the mod under test, so a test run is not disturbed by whatever else is installed. Saves that were edited with two other mods installed loaded without them. (2026-10-03, game 502094, SML 3.12.0)
- **A small window cuts the GPU load of automated test runs by a third; the game stores the window arguments in the user's settings.**
  - `-windowed -ResX=640 -ResY=480` gives a window of 960×720 real pixels at 150 % display scaling. During the same train scenario the GPU board power fell from 43.4 W to 33.9 W on average (idle desktop 16–17 W, so about a third less above idle) and from 55 W to 40 W at the peak. The game's CPU use (2 cores) and frame rate (59 fps, capped at 60) did not change, and the scenario's result lines were the same.
  - Setting the scalability groups to 0 on top of the small window changed nothing measurable; the tester's settings already had most groups at 0.
  - The game rewrites `%LOCALAPPDATA%\FactoryGame\Saved\Config\Windows\GameUserSettings.ini` on every start. A run with `-ResX`/`-ResY` stored the test window there (`ResolutionSizeX/Y`, `LastUserConfirmedResolutionSizeX/Y`, `LastConfirmedFullscreenMode`), so the user's next normal start would have opened in the test window. Copy the file before the run and put it back after the game has closed; with that the file's SHA256 was the same before and after.
  - Quality values are stored twice in that file: in `[ScalabilityGroups]` and inside the `mIntValues=(("sg.…Quality", N),…)` line of `[/Script/FactoryGame.FGGameUserSettings]`. Values edited in both places before the start were kept by the game, except `sg.GlobalIlluminationQuality`, which it put back to 1.
  - (2026-10-03, game 502094, SML 3.12.0)
- **Measuring the GPU load of a run:** sample `nvidia-smi --query-gpu=utilization.gpu,power.draw,temperature.gpu --format=csv,noheader,nounits` every 5 s while the game process exists, together with the game process's CPU seconds and working set; judge only the scenario part (from its first line to its result line) and take the idle value from the samples before the game started. 5 s samples miss short peaks (loading reached 100 % and 119 W between them). Evidence: the 43.4 W and 33.9 W averages above were measured this way. (2026-10-03, game 502094, SML 3.12.0)
- **The game client cannot run without a renderer.** Started with `-nullrhi`, with only SML and the tested mod loaded, the packaged client loaded a save, ran the mod's first tick and died about 10 s later: `EXCEPTION_ACCESS_VIOLATION reading address 0x00000000000002e0` in the game's own `UFGTextRenderer::TickComponent` (`FGTextRenderer.cpp:54`) calling `UCanvas::K2_DrawText`. The frame counter moved only from 54 to 64 in those 10 s. So automated tests on the client need the renderer. **[?]** A dedicated server is the renderer-free target; it was not tried. **[?]** The SML 3.12 guide in the docs says the engine no longer loads mesh data under `-nullrhi` (a server memory optimisation), which fits a client that dies in its first frames. A windowless but rendering alternative is `-RenderOffScreen`, which ran a client cleanly (`references/testing-launch.md`). A mod's own GPU code can also crash a client started with `-nullrhi`: see "A render target (any texture) has no resource when the game cannot render" in `domains/rendering/render-targets.md`. (2026-10-03, game 502094, SML 3.12.0)
- **A game that hangs on exit can stay in the process list and keep its files locked until it is ended from Task Manager.** After an automated run the game logged `LogExit: Preparing to exit.` and `Shutting down movie player`, then hung. `taskkill /F` answered "There is no running instance of the task", `Stop-Process -Force` returned without error, `Get-Process` showed it with `HasExited = True` and 4 GB of memory, and it still held `FactoryGame.log` open, so a new run could not rename the log. It did not go away in minutes. A test script should count only processes with `HasExited = false` as a running game.
  - A second hang (same log tail) again ignored `taskkill /F` ("no running instance") and `Stop-Process -Id <pid> -Force`, and it held the mod's DLLs and `.utoc`/`.ucas` locked (`cp`: "Device or resource busy"), so a new build could not be installed. Ending it from Windows Task Manager worked, where it was listed under a different name ("FactoryGame Studio"); after that `tasklist` showed no game, the files were free and the next run packaged and installed normally. So: ask the user to end the game in Task Manager (look for a FactoryGame entry), and restart Windows only if that fails too. **[?]** Why Task Manager succeeds where `taskkill /F` and `Stop-Process -Force` fail. (2026-10-04 and 2026-10-05, game 502094, SML 3.12.0, Windows 11)

- **`FParse::Value` into an `FString` stops at a comma unless told not to.** `FParse::Value(FCommandLine::Get(), TEXT("MyArg="), Out)` with `-MyArg=1,2,3` gives `1`; with `bShouldStopOnSeparator = false` (`FParse::Value(..., Out, false)`) it gives `1,2,3`. Evidence: a test's shape parameter of five numbers was read as one until the flag was set. (2026-10-23, UE 5.6.1-CSS)
- **A large save loaded without the mods it was made with looks hung on the loading screen.** Each object of a missing mod's class costs about 85 ms while loading (`LogUObjectGlobals: Warning: Failed to find object '...PersistentLevel.<Mod>_<Class>_<n>'`, several lines per object, plus `LogSave: Warning: Got object [...] of deleted class [...]`), so a save with thousands of them stays minutes on the loading screen while the log keeps growing. A test run on the player's own modded save must load the player's mods (the same save loaded in 15 s with them, and was still loading after 4 min and 2700 such lines without them). A log that still grows tells a slow load from a hang. (2026-10-23, game CL 513885, SML 3.12.0)
- A `loadgame=` option for a save that does not exist starts a **new** world, silently: no `World Serialization (load)` line, no error or warning naming the save, and the game mode's options still carry the name (`?Name=Player?skipOnboarding?listen?loadgame=<missing>`, exit code 0). A test that loads a save by name must check that the load happened, or it runs on a fresh world: the line `LogGame: World Serialization (load): 0.132 seconds` must exist. It carries no save name; the name is only in the `LoadMap:`/`Browse:` line, which a missing save has too. **[?]** The docs also say a save from a newer game version falls back to a new world; a copy of a good save with only the header changed to SaveVersion 160 and build 999999 loaded through `?loadgame=` with no version warning, so a header alone does not make a save unloadable on that path; a save really written by a newer game was not available, so the docs' claim is unproven. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **A save's header names the mods it was made with, and a test save can be checked before a run.** The header starts with uncompressed JSON, `{"Version":1,"Mods":[{"Reference","Name","Version"}],"FullMapName":"…"}`; the first ~300 bytes of the `.sav` file show it. Evidence: the header of a test save read on disk. **[source]** SML writes it at `POST_INITIALIZATION` on the authority (`SML/Private/…/SMLWorldModule.cpp:31-52`); a mod that calls `SetModMetadata` replaces SML's list (tested, `references/sml-config-networking.md`, "Save header"). On load SML warns only about a mod that is missing and about a loaded mod older than the saved one (`SaveMetadataPatch.cpp:147-156`); the console variable `SML.SkipModCompatibilityCheck` skips the check and defaults to 1 in the editor (`:14-19`). A save loaded without the mods in its header: see the slow load above. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

The recipe keeps `Manifest_*_Win64.txt`, `FactoryGame\Configs` and `FactoryGame\Mods` of the install, renames `Saved\Config`, deletes `*.upipelinecache` in `Saved`, and starts the copy standalone with `-NoSteamClient -EpicPortal` (needs `steam_appid.txt`, see above); saves for a copy started without the launcher go to `SaveGames\common`. Only the depot ID was checked. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

Not built in a mod yet. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)

**Pre-release checklist**
- [ ] Package all the targets you release (Steam, EGS, Win/Linux servers).
- [ ] Small and large save; new game.
- [ ] 3 save loads in a row and a return to the menu: VRAM and RAM stable, no mod errors after loading, i.e. nothing leaks from the previous world.
- [ ] Multiplayer: host + client; dedicated server.
- [ ] Log without mod errors and warnings.
- [ ] `SemVersion` and `VersionName` bumped, `GameVersion` correct.
- [ ] Changelog with the numbers from your measurements and a list of what you did not test.
