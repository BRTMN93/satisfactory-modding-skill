# Testing, release, ficsit.app, working with someone else's mod

Part of the `satisfactory-modding` skill. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

## 16. Testing and the pre-release checklist

**Rules**
- Test in the packaged game (rule 1 in `SKILL.md`).
- **Back up the saves before testing.** A copied save keeps its session name, so autosaves during testing overwrite the rotating slots of the *original* session. Rename the test session or turn autosave off (console variable `FG.AutosaveInterval = 0`).
- Launch parameters that change the resolution stay in the game's screen settings (`GameUserSettings.ini`), so the next normal start would open in the test window. Copy the file before the test and put it back after the game has closed (details under "Launching the game for tests").
- When measuring performance, record the conditions. Fullscreen and a borderless window give different results, and with frame generation the engine's frame times are not the same as the displayed frames.
- Manual tests: numbered steps, with a log-watching script confirming each step. Before saving the game, wait until the background work finishes.
- Automation: a separate test mod enabled by a launch parameter (e.g. `-MyModTestBridge`) reads commands from a file (`commands.jsonl`), loads saves, builds and dismantles buildings, samples frame times and memory, and writes the results to files. I picked this pattern up from another modder.
- Check rendering changes by comparing images pixel by pixel (old and new build, same save).

- **A test save built under another mod profile loses buildables when it is re-saved without those mods.** Track pieces and a conveyor lift were missing after a save was loaded and saved again in a profile with only SML. The save's session settings still carried the other profile's mod settings (`SessionSettings=...InfiniteZoop.BlueprintZoop=...` in `LogGameMode: ProcessServerTravel`). Build and change test saves only in the test profile, and after every change check them in the game, for example with one full lap of a test train. (2026-10-02, game 502094, SML 3.12.0)

**Launching the game for tests**
- **Starting the game straight into a save works** (docs.ficsit.app, Development → Testing). Launch `<Game>\FactoryGameSteam.exe` with:
  `-ini:Engine:[/Script/EngineSettings.GameMapsSettings]:GameDefaultMap=/Game/FactoryGame/Map/GameLevel01/Persistent_Level.Persistent_Level,[/Script/EngineSettings.GameMapsSettings]:LocalMapOptions=?skipOnboarding?listen?loadgame=<save name without path and extension>`
  - The argument has no spaces, so `Start-Process -ArgumentList @(...)` passes it unquoted.
  - The Steam client must be running.
  - **The Steam copy also needs `<Game>\Engine\Binaries\Win64\steam_appid.txt` containing `526870`.** Without it the log shows `LogSteamShared: Warning: SteamAPI failed to initialize, conditions not met.` and `LogOnlineServices: Game restarting within Steam client, exiting`. Steam then starts a second copy with only `-NO_EOS_OVERLAY`. That copy writes `FactoryGame_2.log`, because the first copy still holds the log. All your arguments are lost and the game sits in the main menu.
  - The root `FactoryGameSteam.exe` is a stub that stays alive next to `FactoryGameSteam-Win64-Shipping`.
  - On a 180 KB save it took 16–20 s from `Start-Process` to the world's BeginPlay.
  - Evidence: `LogInit: Command Line:` shows the arguments, then `LogGame: World Serialization (load)`.
  - **The local player does not get the character stored in the save.** It spawns somewhere else, and the stored character stays in the world as an idle pawn named "player". This was reported by the user from the packaged game. It is harmless for scenarios that do not need the player. Do not save the game from such a session, though, or the save gains a second player. **[?]** The cause has not been checked. The likely one is a different player identity than in a normal Steam start.
  - **The new player starts with empty player rules, so the advanced game setting "flight" is off** even when the saved player had it. Flight is a per-player rule (`FPlayerRules::FlightMode` in `FGPlayerState.h`). Calling `AFGPlayerState::SetFlightMode(true)` on the local player's state, once `UFGBlueprintFunctionLibrary::GetLocalPlayerController(World)->GetPawn()` exists, changed `GetPlayerRules().FlightMode` from 0 to 1 about one second after the world started. That the character can then fly was confirmed by the user in the packaged game.
  - The loaded save's name can be read back with `FParse::Value(FCommandLine::Get(), TEXT("loadgame="), Name)`. The value stops at the space before the next argument. Useful for a test that saves again under the same name.
  - **[?]** Leaving such a session through the menu loaded the same save again (`LoadMap: ...?closed?skipOnboarding?listen?loadgame=<save>` right after the player saved and left). The likely cause is that the `-ini` override of `LocalMapOptions` also applies to the map the menu goes back to. Seen once.
- **A developer test mode behind a custom launch parameter works in Shipping.**
  - `FParse::Value(FCommandLine::Get(), TEXT("MyModTest="), Name)` reads `-MyModTest=<Name>`.
  - Start the scenario on the next tick after the world module's `POST_INITIALIZATION`.
  - Write steps and the result to the log under a fixed tag.
  - Close the game afterwards with `GLog->Flush()` and then `FPlatformMisc::RequestExit(false, TEXT("<call site>"))`. This logs `FPlatformMisc::RequestExit(0, <call site>)` and `Engine exit requested`, then shuts down cleanly (`LogExit: Exiting.`) in about 7 s.
  - A script that reads the log should move the old `FactoryGame.log` aside itself before the launch, so no line from an earlier run is mistaken for a result.
  - One cycle from launch to result took 22–24 s without packaging and 48–71 s with incremental packaging of an unchanged mod.
  - Scenarios that wait for the game, such as a train run, can end later from a timer or a delegate.
- Three loads of a save in one game process, with a return to the real main menu in between, work from test code while the game was started with the `-ini` override of `GameDefaultMap`/`LocalMapOptions`: `UGameplayStatics::OpenLevel(World, FName(TEXT("/Game/FactoryGame/Map/MenuScenes/Map_Menu_1_02")))` goes to the menu (`LogLoad: LoadMap: /Game/FactoryGame/Map/MenuScenes/Map_Menu_1_02`), and `UGameplayStatics::OpenLevel(MenuWorld, FName(TEXT("/Game/FactoryGame/Map/GameLevel01/Persistent_Level")), true, TEXT("skipOnboarding?listen?loadgame=<save>"))` loads the save again. Drive it from the core ticker (`FTSTicker`), which survives the world changes, and wait about 3 s in each new world. A `CollectGarbage` called from that ticker in the menu ran without trouble, so a test can count the mod's objects still alive after each world. Errors the game itself logs on every such load (navmesh bounds, session widgets in the menu) are not the mod's. Evidence: packaged-game log of 2026-10-03 20:24 UTC. (2026-10-03, game 502094, SML 3.12.0)
- A test that waits on the core ticker (`FTSTicker::GetCoreTicker()`, the way to survive world changes) must count game frames, not only wall-clock seconds. After a save had loaded, the world had begun play and the player's `UFGGameUI` existed, yet the game sat in one frame for 17 s (frame number 35 → 36 in the log brackets while the ticker kept running); `AFGHUD::OpenInteractUI` called then left no window on the interact stack 1.5 s later. Waiting until both the seconds and at least 10 frames (`GFrameCounter`) have passed fixed it, and the same windows opened every time in three loads in one process. Evidence: `<TEST_TAG> step FAILED …: window open: None` at frame 36, then PASS with 186 checks after the change. (2026-10-03, game 502094, SML 3.12.0)
- A logic module that only compares game objects through weak-pointer handles can be self-tested in the packaged game without any game object: `NewObject<UObjectRedirector>(GetTransientPackage())` gives a real, distinct `UObject` per call (the class is exported from CoreUObject and concrete, `UObject` itself is abstract), so the test module needs only `Core` and `CoreUObject`. The objects are unreferenced, so keep the whole test inside one tick. Evidence: a self-test of 84 checks built this way passed in a Shipping build, started by a launch parameter after the world loaded. (2026-10-03, game 502094, SML 3.12.0, UE 5.6.1-CSS)
- **`-DisablePlugins=A,B` starts the game without the named mods and leaves their files alone.** The engine reads the parameter in Shipping builds too (`FPluginManager::ConfigureEnabledPlugins`, `<UE-CSS>/Engine/Source/Runtime/Projects/Private/PluginManager.cpp`). The log then says `LogPluginManager: Display: Skipping loading modules for <Mod>. Plugin is not enabled for current target.` and SML's list of loaded mods (`LogSatisfactoryModLoader: Display: <Mod>: <version>`) leaves the mod out. A test script can pass every `*.uplugin` name found under `FactoryGame\Mods` except SML and the mod under test, so a test run is not disturbed by whatever else is installed. Saves that were edited with two other mods installed loaded without them. (2026-10-03, game 502094, SML 3.12.0)
- **A small window cuts the GPU load of automated test runs by a third; the game stores the window arguments in the user's settings.**
  - `-windowed -ResX=640 -ResY=480` gives a window of 960×720 real pixels at 150 % display scaling. During the same train scenario the GPU board power fell from 43.4 W to 33.9 W on average (idle desktop 16–17 W, so about a third less above idle) and from 55 W to 40 W at the peak. The game's CPU use (2 cores) and frame rate (59 fps, capped at 60) did not change, and the scenario's result lines were the same.
  - Setting the scalability groups to 0 on top of the small window changed nothing measurable; the tester's settings already had most groups at 0.
  - The game rewrites `%LOCALAPPDATA%\FactoryGame\Saved\Config\Windows\GameUserSettings.ini` on every start. A run with `-ResX`/`-ResY` stored the test window there (`ResolutionSizeX/Y`, `LastUserConfirmedResolutionSizeX/Y`, `LastConfirmedFullscreenMode`), so the user's next normal start would have opened in the test window. Copy the file before the run and put it back after the game has closed; with that the file's SHA256 was the same before and after.
  - Quality values are stored twice in that file: in `[ScalabilityGroups]` and inside the `mIntValues=(("sg.…Quality", N),…)` line of `[/Script/FactoryGame.FGGameUserSettings]`. Values edited in both places before the start were kept by the game, except `sg.GlobalIlluminationQuality`, which it put back to 1.
  - (2026-10-03, game 502094, SML 3.12.0)
- **The game client cannot run without a renderer.** Started with `-nullrhi`, with only SML and the tested mod loaded, the packaged client loaded a save, ran the mod's first tick and died about 10 s later: `EXCEPTION_ACCESS_VIOLATION reading address 0x00000000000002e0` in the game's own `UFGTextRenderer::TickComponent` (`FGTextRenderer.cpp:54`) calling `UCanvas::K2_DrawText`. The frame counter moved only from 54 to 64 in those 10 s. So automated tests on the client need the renderer. **[?]** A dedicated server is the renderer-free target; it was not tried. A mod's own GPU code can also crash a client started with `-nullrhi`: see "A render target (any texture) has no resource when the game cannot render" in `references/rendering-ui.md`. (2026-10-03, game 502094, SML 3.12.0)
- **A game that hangs on exit can stay in the process list and keep its files locked until it is ended from Task Manager.** After an automated run the game logged `LogExit: Preparing to exit.` and `Shutting down movie player`, then hung. `taskkill /F` answered "There is no running instance of the task", `Stop-Process -Force` returned without error, `Get-Process` showed it with `HasExited = True` and 4 GB of memory, and it still held `FactoryGame.log` open, so a new run could not rename the log. It did not go away in minutes. A test script should count only processes with `HasExited = false` as a running game.
  - A second hang (same log tail) again ignored `taskkill /F` ("no running instance") and `Stop-Process -Id <pid> -Force`, and it held the mod's DLLs and `.utoc`/`.ucas` locked (`cp`: "Device or resource busy"), so a new build could not be installed. The user ended it from Windows Task Manager, where it was listed under a different name ("FactoryGame Studio", as the user reported); after that `tasklist` showed no game, the files were free and the next run packaged and installed normally. So: ask the user to end the game in Task Manager (look for a FactoryGame entry), and restart Windows only if that fails too. **[?]** Why Task Manager succeeds where `taskkill /F` and `Stop-Process -Force` fail. (2026-10-04 and 2026-10-05, game 502094, SML 3.12.0, Windows 11)
- **[source]** The documentation also gives a ready-made PowerShell script for launching the game (with, among others, the parameters `-loadLatestSave` and `-multiplayer`) and the parameters `-EpicPortal`, `-NoSteamClient`, `-log`, `-NewConsole`, `-nosplash`, `-windowed`, `-WaitForDebugger`. **Watching a series of automated runs while it goes**
- A packaged test run takes minutes (packaging 2–5 min, the game 1–20 min), so a series ties up the machine for an hour or more, and a broken run that is only read at its time limit wastes all of it.
  - While a run goes, check the game log every 30 s, not only at the end: the scenario's failure lines, the mod's warnings and errors, `Fatal error`, a crash report, and a run that has logged nothing new for a few minutes. Stop a run that has already failed instead of waiting for its time limit, and note at once when something done in the test window (a click, getting into a vehicle, a changed setting) disturbed it.
  - The watching can go to a sub-agent on the cheapest model (Haiku), not to the main model: it costs a few tool calls per run instead of the main session's context. The sub-agent runs a small shell script in a loop. The script reads only the log lines added since the last call, every 30 s, prints the first problem lines (deduplicated, without timestamps) or a "no new step for N s" line, then the number of lines it has read, and exits. The sub-agent sends what was printed verbatim to the main session (`SendMessage` to `main`), starts the script again from that line number, and stops after the result line. The main session reacts only to those messages. Start the first call from the current line count of the log (`wc -l < FactoryGame.log`) and its id (`head -n 1 FactoryGame.log | tr -dc '0-9.:-'`), not 0: until the new game start renames it, the log still holds the previous run, and from 0 the watcher reports that run's result as the new one. The script resets to 0 itself when the log shrinks. A run shorter than the 30 s step (a self-test that ends 25 s after the start, followed at once by the next run) can come and go between two reads, and the watcher then misses its result: the main session always reads the result line of the test script itself too.
  - Late reports of an earlier run (seen in practice: a watcher's hand-back arrived after the next run had started and read like news) are prevented three ways: (1) every report of the script starts with a line `RUN <test> started <time in the log>`, and the sub-agent passes it on unchanged, so the main session compares it with the run it started and drops anything older; (2) before it starts a new run, the main session stops the previous watcher (`TaskStop`), so nothing of it can arrive later; (3) the findings go only through `SendMessage`, and the sub-agent's final hand-back is the single word `done`, not a second copy of the result.
  - A watcher also ends itself: the script prints `GAME CLOSED, watch over` once the game process is gone and new log lines came since the last call (a closed or killed game, a run without a result), and the sub-agent stops on that line as on a result. While the run still packages and starts there is no game process yet; the script prints `game not started yet` then and the watcher keeps looping. The main session, for its part, stops the watcher (`TaskStop`) as soon as it has the result from the test script, whatever the watcher has said by then.
  - Evidence: a 20-minute run stood still for about 4 minutes because a station's setting was changed in the test window, and was noticed only when the user reported the waiting train. (2026-10-04, game 502094, SML 3.12.0)
- **A second watcher looks at behaviour, not only at results.** The result watcher above reports failed checks, warnings and the result. A scenario can run for an hour with none of those while the mod misbehaves in a way a player would spot in a minute (seen on 2026-10-06: a move command re-issued every 10 s because the mod ended it a second after it began, with every check green). Next to the result watcher, run a second sub-agent on a model that can reason (Sonnet) with a list of behavioural anomalies to report at once, with the evidence lines verbatim: the same command repeated for one train, a train standing at a signal or with an autopilot error for more than a minute while it has work, a job stuck in one state for more than ten minutes, an order reason flipping between two values every cycle, two pool trains at one station, a loaded train without a job, plus the mod's warnings and the result line. Give it the shape of the status lines so it can read them, a list of what is normal (so it does not report design behaviour), a start time so it ignores the previous run's log, and a cap on iterations. The owner asked for this watcher after catching such a loop by eye.
- **The watcher script is `scripts/watch-run.sh`** (bash, Git Bash on Windows), so no session has to write it again. Call it `bash watch-run.sh <test> <from_line> [<log_id>]`; the mod's log category and the prefix of the scenario's log lines come from the environment (`MOD_LOG_CATEGORY`, `TEST_TAG`; see the header of the script). It waits 30 s, reads the game log from the given line and prints `RUN <test> started <time>`, the new problem lines (failed checks, `RESULT`, the mod's warnings and errors, `Fatal error`), `no new step for 30 s`, and `LINES <n> <id>`; it resets to line 0 when the log shrank or its id changed (a new game start renames the old log). Evidence: Haiku sub-agents looping on it watched 9 runs of 2–20 minutes on 2026-10-05, reported failed checks and results, and stopped by themselves. Mistakes that cost runs that day, each fixed in the script or the prompt:
  - **The game is not running yet while the run packages and starts** (1–3 minutes). A first version printed `GAME CLOSED, watch over` then and the watcher stopped before the game came up. The script now prints it only when the game process is gone *and* new log lines came since the last call, and otherwise `game not started yet`, on which the watcher keeps looping.
  - **The start line has to be read, not guessed.** `wc -l < FactoryGame.log` right before the run starts; a number below the real length made the first call read the previous run's last lines, see no game and stop at once.
  - **Expected noise goes into the prompt as lines to ignore.** With the mod's developer mode on, a self-test after every load logs a dozen deliberate `Rejected …` warnings; a watcher that forwards them makes the main session read them every run.
  - **A new log is recognised by its first line, not only by its length.** One watcher missed a run's `RESULT` and kept watching the next game: comparing the line count with the last one does not tell the new log from the old one when the new log is already longer by the first read. The script takes a third argument, the first line of the log as last seen (`Log file open, <date> <time>` reduced to digits), prints it as `LINES <n> <id>`, and reads from line 0 when it changed.
  - **The watcher script met the moment without a log file.** The game renames its old log when it starts, so for a moment `FactoryGame.log` does not exist. `scripts/watch-run.sh` then printed the shell's own error (`…FactoryGame.log: No such file or directory`, from the `wc -l < "$LOG"` redirection, which fails before `2>/dev/null` applies) and `LINES 0` with no id, and the watching sub-agent forwarded that as a problem line. The script now checks for the file first and prints `game not started yet` with the caller's own `LINES <from> <id>`. Evidence: a watcher's message during a run's start, `line 23: …FactoryGame.log: No such file or directory`, `LINES 0`. (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)
  - **A watcher that counts every tagged line as progress misses a run that stands still.** A scenario that prints a status table every 30 s while it waits kept `watch-run.sh` quiet for 20 minutes although nothing happened (the train it waited for was switched out of the mod's control in that save). `watch-run.sh` now takes `STATUS_PATTERN`, an extended regex of such status lines; they no longer count as a new step. Also give every scenario its own short limit for "nothing started yet" (e.g. fail when no job was sent after 3 minutes) and let the watcher report "no new step" after about 2 minutes, not 5. Evidence: a 21-minute stall with only status lines in the log; the pattern left 0 progress lines of 32 in the stalled window. (2026-10-06, game 502094, SML 3.12.0)
  - **Two runs in one command** (a writer scenario, then the one that loads its save): a single watcher told to stop after the second `RESULT` did not stop and was still running 20 minutes later, sending stray shell errors into the conversation. One watcher per run instead, and the main session stops every watcher (`TaskStop`) as soon as it has the run's result from the test script, as above; the slip was not doing it.
  - **A queue of runs needs one watcher per run, too.** A single Haiku watcher told to watch a five-run queue (one script that runs the scenarios one after another) and to stop after 5 `RESULT` lines kept going after the queue ended: one run had no `RESULT` (its game was closed by hand after a deadlock), so the watcher was one short, took the next game (a manual test with the user, which never prints steps) for a run and reported a false 3-minute stall. This is the "two runs in one command" slip again. For a queue, start a fresh watcher whenever the queue script prints its line for a finished run (e.g. `QUEUE 04 <scenario> exit 1`), or stop the watcher with `TaskStop` as soon as the queue prints its last line. Evidence: the false `STALL … (<scenario>)` came 12 minutes after `QUEUE done`. (2026-10-06, game 502094, SML 3.12.0, Haiku 4.5)
  - **Stop the old watchers before starting the new ones.** When a run ends, first `TaskStop` both of its watchers (a result watcher sometimes keeps looping when its first read landed in the previous game), then spawn the pair for the next run. In practice a watcher of one run was still alive while the next run already had its own pair.
  - **A run shorter than the watcher's first wait gets no watcher.** An autotest scenario that ends 23 s after the world loads was over, and its log renamed by the next run of the queue, before the watcher's first read; the watcher then sat on the next game for ten iterations ("still loading"). For such runs read the queue's `QUEUE NN <Test> exit <code>` line and the copied log instead, and start the next run's pair from the new log's id.
  - Prompt that worked (Haiku): loop `bash watch-run.sh <test> <FROM> <ID>`, take `LINES n id` as the next FROM and ID, forward the output verbatim with `SendMessage` to `main` only when it holds a line other than `RUN`, `no new step`, `game not started yet`, `LINES` and the listed noise, stop after `RESULT` or `GAME CLOSED, watch over`, final answer the single word `done`. One of three watchers shortened what it forwarded: it sent only the `RESULT` line instead of the whole output with its `RUN <test> started` line, and ended with a sentence instead of `done`, so the main session could not tell which run the message belonged to. The prompt now says "send the WHOLE output of that call verbatim, every line including the `RUN` line" and "Your final answer is the single word `done`, nothing more." (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)

**Working discipline for a series of tests** (a set of working conventions that proved useful, not game facts)
- **When the main model's quota is nearly gone, hand the whole closing to one sub-agent.** With 2% of the main model's weekly limit left, the main session wrote one self-contained brief (rules, repositories, git identity, the running queue and where its output goes, the checks for each run, the build command, the documents to update and how the previous chat recorded them, the commit messages, the final report's shape and length, "never ask the user", "do not message me before the end") and started one Opus agent in the background. The agent finished the series, built twice, found and fixed two failing runs on its own (a host flag after a second load in one process, a race in a scenario between restoring stock and switching planning on), wrote the documents, committed and pushed both repositories, and reported in 8 lines; about 290k tokens, 122 tool calls, 81 minutes. What helps: point it at the checkpoint file and the review report instead of restating them; say which paths the repository ignores (it could not commit the results folder because `.gitignore` excludes it, and said so). The main session answered nothing in between and used almost no tokens.
- **Every FAIL of the closing series was the scenario, not the mod.** Twice in one series the mod was right and the scenario wrong: a flag the scenario set once per process and did not reset on the second load, and two things done in one tick (restore stock, switch planning on) that the next frame's cycle saw in the wrong order. Before changing mod code for a FAIL, read the scenario's own steps around the failing check first.
- **Announce a series.** Before the series starts, show a table: number, scenario, save, what the run checks, state (waiting, running, PASS, FAIL) and time (estimated, then measured). Show the full table only before the first run (and when the series changes or the user asks). Before each later run say in one line only which run comes next (number, scenario, what it checks, estimated time). After each run, one line with the X-of-Y counter and the result. Leave out repeats: every run should add something new. Every run, also inside a queue, has a watcher that reports its result at once, so a run that ended without a result (a closed game window) is noticed.
- **A mechanism checked on one track layout is not verified.** For a mechanism that depends on the tracks, list the popular layouts where it may behave differently (passing loop, siding, junction, two-way single track, dead end, station with several platforms), test those that fit in the session, give the user the list of what to build for the rest, and write the rest into the backlog with the session that will check it.
- **Every "not checked" item goes into a backlog with the session that will check it, and leaves it only with evidence from the game** (a log line, a test result, the user's confirmation), never with reasoning or an opinion. Release is blocked while any item is open; the list does not shrink without a note in the findings.
- **Independent review of production code.** A fresh sub-agent gets the diff, the task description and the rules, but not the author's conclusions. In practice it found 1 to 9 critical bugs per session; critical remarks are fixed at once, the others go to the backlog.
- **Build lists for test layouts.** Give lengths and gaps in Foundations (one Foundation is 8 m) with positions along the line, not in metres, and add a schematic for every rebuild (tracks, stations with the direction arrow, switches, signals split into path and block signals, direction of one-way tracks). A small change such as one more signal needs no schematic. Use the game's English names for buildings and ports. Check the signals against the placement rules in `references/railroad.md` instead of composing them from memory. After the build, first dump the signals from the save (type, direction, block error) and compare the dump with the list, and only then run the scenarios.

**Pre-release checklist**
- [ ] Package all the targets you release (Steam, EGS, Win/Linux servers).
- [ ] Small and large save; new game.
- [ ] 3 save loads in a row and a return to the menu: VRAM and RAM stable, no mod errors after loading, i.e. nothing leaks from the previous world.
- [ ] Multiplayer: host + client; dedicated server.
- [ ] Log without mod errors and warnings.
- [ ] `SemVersion` and `VersionName` bumped, `GameVersion` correct.
- [ ] Changelog with the numbers from your measurements and a list of what you did not test.

## 18. Publishing, ficsit.app, licenses, working with someone else's mod

### ficsit.app (SMR)
- **When the user plans a new mod, search ficsit.app through the API, not with a web search engine.** The web search engine did not find any of the existing railway mods, including a mod with 60 thousand downloads. The API found them at once. Search with several words from the domain (for example: train, station, logistic, dispatch).
- Search through the API. Several queries at once are separated by aliases (`a:`, `b:`):
  ```bash
  curl -s https://api.ficsit.app/v2/query -H "Content-Type: application/json" \
    -d '{"query":"{ a: getMods(filter: {search: \"train\", limit: 40, order_by: downloads, order: desc}) { mods { name mod_reference short_description downloads } } }"}'
  ```
- A `getModByReference` that returns `null` means the mod reference is free.
- The mod owner publishes releases.
- Each game branch (EA/EXP) has a compatibility state flag (e.g. `Works`, `Damaged`, `Broken`) and a note. The owner or the SMR moderators set it.
- Check a mod's state through the API:
  ```bash
  curl -s https://api.ficsit.app/v2/query -H "Content-Type: application/json" \
  ```

### Licenses and forks
- Before forking or releasing someone else's mod, check the license: `gh api repos/O/R/license --jq .license.spdx_id`.
- GPL-3.0 allows releasing a fork, but you must keep the license, make the source available and credit the author.
- A fork is released under a **different mod reference**.
- First try to contact the author: an issue or PR, the Satisfactory Modding Discord, ficsit.app.

### Contributing to someone else's mod (GitHub)
- Reconnaissance: `gh issue list`, `gh pr list` and `view` with `-R o/r --json … --jq …`. Someone may have already fixed the same thing. If so, credit them in the description.
- Fork and PR:
  ```
  gh repo fork o/r --clone=false --default-branch-only
  git remote add fork <url>
  git push -u fork <branch>
  gh pr create -R o/r --base <default> --head <you>:<branch> --body-file description.md
  ```
  Mod repositories often have a default branch other than `master`.
- Send fixes and new features as separate PRs, and within a PR as separate commits, so that the author can reject a part.
- A PR that depends on a previous one targets the author's default branch and contains the previous one's commits. Write in the description "Stacked on #N, only the last commit is new".
- Mod repositories usually have no CI, so **test evidence goes into the PR description**: the engine tag, the game changelist, the build target, the save size, the measured numbers and what you did not test.
- Describe other people's findings that you carry over in the commit ("Thanks to X for finding this, see X/Repo@sha"). This does not make them co-authors.
