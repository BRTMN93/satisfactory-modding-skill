# Test automation: watching runs, series, sub-agents

Part of the `satisfactory-modding` skill. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

How to start the game for a test and the test mode itself: `references/testing.md`. The watcher script is `scripts/watch-run.sh`.

**Watching a series of automated runs while it goes**
- A packaged test run takes minutes (packaging 2–5 min, the game 1–20 min), so a series ties up the machine for an hour or more, and a broken run that is only read at its time limit wastes all of it.
  - While a run goes, check the game log every 30 s, not only at the end: the scenario's failure lines, the mod's warnings and errors, `Fatal error`, a crash report, and a run that has logged nothing new for a few minutes. Stop a run that has already failed instead of waiting for its time limit, and note at once when something done in the test window (a click, getting into a vehicle, a changed setting) disturbed it.
  - The watching can go to a sub-agent on the cheapest model (Haiku), not to the main model: it costs a few tool calls per run instead of the main session's context. The sub-agent runs a small shell script in a loop. The script reads only the log lines added since the last call, every 30 s, prints the first problem lines (deduplicated, without timestamps) or a "no new step for N s" line, then the number of lines it has read, and exits. The sub-agent sends what was printed verbatim to the main session (`SendMessage` to `main`), starts the script again from that line number, and stops after the result line. The main session reacts only to those messages. Start the first call from the current line count of the log (`wc -l < FactoryGame.log`) and its id (`head -n 1 FactoryGame.log | tr -dc '0-9.:-'`), not 0: until the new game start renames it, the log still holds the previous run, and from 0 the watcher reports that run's result as the new one. The script resets to 0 itself when the log shrinks. A run shorter than the 30 s step (a self-test that ends 25 s after the start, followed at once by the next run) can come and go between two reads, and the watcher then misses its result: the main session always reads the result line of the test script itself too.
  - Late reports of an earlier run (seen in practice: a watcher's hand-back arrived after the next run had started and read like news) are prevented three ways: (1) every report of the script starts with a line `RUN <test> started <time in the log>`, and the sub-agent passes it on unchanged, so the main session compares it with the run it started and drops anything older; (2) before it starts a new run, the main session stops the previous watcher (`TaskStop`), so nothing of it can arrive later; (3) the findings go only through `SendMessage`, and the sub-agent's final hand-back is the single word `done`, not a second copy of the result.
  - A watcher also ends itself: the script prints `GAME CLOSED, watch over` once the game process is gone and new log lines came since the last call (a closed or killed game, a run without a result), and the sub-agent stops on that line as on a result. While the run still packages and starts there is no game process yet; the script prints `game not started yet` then and the watcher keeps looping. The main session, for its part, stops the watcher (`TaskStop`) as soon as it has the result from the test script, whatever the watcher has said by then.
  - Evidence: a 20-minute run stood still for about 4 minutes because a station's setting was changed in the test window, and was noticed only when someone looked at the waiting train. (2026-10-04, game 502094, SML 3.12.0)
- **A second watcher looks at behaviour, not only at results.** The result watcher above reports failed checks, warnings and the result. A scenario can run for an hour with none of those while the mod misbehaves in a way a player would spot in a minute (seen on 2026-10-06: a move command re-issued every 10 s because the mod ended it a second after it began, with every check green). Next to the result watcher, run a second sub-agent on a model that can reason (Sonnet) with a list of behavioural anomalies to report at once, with the evidence lines verbatim: the same command repeated for one object, an object standing still or in an error state for more than a minute while it has work, a task stuck in one state for more than ten minutes, a value flipping between two states every cycle, two objects claiming one place, a loaded object without a task (for a train mod: a train waiting at a signal, two trains at one station), plus the mod's warnings and the result line. Give it the shape of the status lines so it can read them, a list of what is normal (so it does not report design behaviour), a start time so it ignores the previous run's log, and a cap on iterations.
- **The watcher script is `scripts/watch-run.sh`** (bash, Git Bash on Windows), so no session has to write it again. Call it `bash watch-run.sh <test> <from_line> [<log_id>]`; the mod's log category and the prefix of the scenario's log lines come from the environment (`MOD_LOG_CATEGORY`, `TEST_TAG`; see the header of the script). It waits 30 s, reads the game log from the given line and prints `RUN <test> started <time>`, the new problem lines (failed checks, `RESULT`, the mod's warnings and errors, `Fatal error`), `no new step for 30 s`, and `LINES <n> <id>`; it resets to line 0 when the log shrank or its id changed (a new game start renames the old log). Evidence: Haiku sub-agents looping on it watched 9 runs of 2–20 minutes on 2026-10-05, reported failed checks and results, and stopped by themselves. Mistakes that cost runs that day, each fixed in the script or the prompt:
  - **The game is not running yet while the run packages and starts** (1–3 minutes). A first version printed `GAME CLOSED, watch over` then and the watcher stopped before the game came up. The script now prints it only when the game process is gone *and* new log lines came since the last call, and otherwise `game not started yet`, on which the watcher keeps looping.
  - **The start line has to be read, not guessed.** `wc -l < FactoryGame.log` right before the run starts; a number below the real length made the first call read the previous run's last lines, see no game and stop at once.
  - **Expected noise goes into the prompt as lines to ignore.** With the mod's developer mode on, a self-test after every load logs a dozen deliberate `Rejected …` warnings; a watcher that forwards them makes the main session read them every run.
  - **A new log is recognised by its first line, not only by its length.** One watcher missed a run's `RESULT` and kept watching the next game: comparing the line count with the last one does not tell the new log from the old one when the new log is already longer by the first read. The script takes a third argument, the first line of the log as last seen (`Log file open, <date> <time>` reduced to digits), prints it as `LINES <n> <id>`, and reads from line 0 when it changed.
  - **The watcher script met the moment without a log file.** The game renames its old log when it starts, so for a moment `FactoryGame.log` does not exist. `scripts/watch-run.sh` then printed the shell's own error (`…FactoryGame.log: No such file or directory`, from the `wc -l < "$LOG"` redirection, which fails before `2>/dev/null` applies) and `LINES 0` with no id, and the watching sub-agent forwarded that as a problem line. The script now checks for the file first and prints `game not started yet` with the caller's own `LINES <from> <id>`. Evidence: a watcher's message during a run's start, `line 23: …FactoryGame.log: No such file or directory`, `LINES 0`. (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)
  - **A watcher that counts every tagged line as progress misses a run that stands still.** A scenario that prints a status table every 30 s while it waits kept `watch-run.sh` quiet for 20 minutes although nothing happened (the train it waited for was switched out of the mod's control in that save). `watch-run.sh` now takes `STATUS_PATTERN`, an extended regex of such status lines; they no longer count as a new step. Also give every scenario its own short limit for "nothing started yet" (e.g. fail when no job was sent after 3 minutes) and let the watcher report "no new step" after about 2 minutes, not 5. Evidence: a 21-minute stall with only status lines in the log; the pattern left 0 progress lines of 32 in the stalled window. (2026-10-06, game 502094, SML 3.12.0)
  - **Two runs in one command** (a writer scenario, then the one that loads its save): a single watcher told to stop after the second `RESULT` did not stop and was still running 20 minutes later, sending stray shell errors into the conversation. One watcher per run instead, and the main session stops every watcher (`TaskStop`) as soon as it has the run's result from the test script, as above; the slip was not doing it.
  - **A queue of runs needs one watcher per run, too.** A single Haiku watcher told to watch a five-run queue (one script that runs the scenarios one after another) and to stop after 5 `RESULT` lines kept going after the queue ended: one run had no `RESULT` (its game was closed by hand after a deadlock), so the watcher was one short, took the next game (a manual test with the user, which never prints steps) for a run and reported a false 3-minute stall. This is the "two runs in one command" slip again. For a queue, start a fresh watcher whenever the queue script prints its line for a finished run (e.g. `QUEUE 04 <scenario> exit 1`), or stop the watcher with `TaskStop` as soon as the queue prints its last line. Evidence: the false `STALL … (<scenario>)` came 12 minutes after `QUEUE done`. (2026-10-06, game 502094, SML 3.12.0, Haiku 4.5)
  - **Stop the old watchers before starting the new ones.** When a run ends, first `TaskStop` both of its watchers (a result watcher sometimes keeps looping when its first read landed in the previous game), then spawn the pair for the next run. In practice a watcher of one run was still alive while the next run already had its own pair.
  - **A run shorter than the watcher's first wait gets no watcher.** An autotest scenario that ends 23 s after the world loads was over, and its log renamed by the next run of the queue, before the watcher's first read; the watcher then sat on the next game for ten iterations ("still loading"). For such runs read the queue's `QUEUE NN <Test> exit <code>` line and the copied log instead, and start the next run's pair from the new log's id.
  - Prompt that worked (Haiku): loop `bash watch-run.sh <test> <FROM> <ID>`, take `LINES n id` as the next FROM and ID, forward the output verbatim with `SendMessage` to `main` only when it holds a line other than `RUN`, `no new step`, `game not started yet`, `LINES` and the listed noise, stop after `RESULT` or `GAME CLOSED, watch over`, final answer the single word `done`. One of three watchers shortened what it forwarded: it sent only the `RESULT` line instead of the whole output with its `RUN <test> started` line, and ended with a sentence instead of `done`, so the main session could not tell which run the message belonged to. The prompt now says "send the WHOLE output of that call verbatim, every line including the `RUN` line" and "Your final answer is the single word `done`, nothing more." (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)

**Working discipline for a series of tests** (a set of working conventions that proved useful, not game facts)
- **When the main model's quota is nearly gone, hand the whole closing to one sub-agent.** The main session wrote one self-contained brief (rules, repositories, git identity, the running queue and where its output goes, the checks for each run, the build command, the documents to update and how the previous chat recorded them, the commit messages, the final report's shape and length, "never ask the user", "do not message me before the end") and started one Opus agent in the background. The agent finished the series, built twice, found and fixed two failing runs on its own (a flag after a second load in one process, a race in a scenario between restoring the test state and switching the mod on), wrote the documents, committed and pushed both repositories, and reported in 8 lines. What helps: point it at the checkpoint file and the review report instead of restating them; say which paths the repository ignores (it could not commit the results folder because `.gitignore` excludes it, and said so). The main session answered nothing in between and used almost no tokens.
- **Every FAIL of the closing series was the scenario, not the mod.** Twice in one series the mod was right and the scenario wrong: a flag the scenario set once per process and did not reset on the second load, and two things done in one tick (restore the test state, switch the mod on) that the next frame's cycle saw in the wrong order. Before changing mod code for a FAIL, read the scenario's own steps around the failing check first.
- **Announce a series.** Before the series starts, show a table: number, scenario, save, what the run checks, state (waiting, running, PASS, FAIL) and time (estimated, then measured). Show the full table only before the first run (and when the series changes or the user asks). Before each later run say in one line only which run comes next (number, scenario, what it checks, estimated time). After each run, one line with the X-of-Y counter and the result. Leave out repeats: every run should add something new. Every run, also inside a queue, has a watcher that reports its result at once, so a run that ended without a result (a closed game window) is noticed.
- **A mechanism checked in one configuration is not verified.** List the configurations where it may behave differently, test those that fit in the session, give the user the list of what to build for the rest, and write the rest into the backlog with the session that will check it. Railway track layouts: `domains/railroad/test-layouts.md`.
- **Every "not checked" item goes into a backlog with the session that will check it, and leaves it only with evidence from the game** (a log line, a test result, the user's confirmation), never with reasoning or an opinion. Release is blocked while any item is open; the list does not shrink without a note in the findings.
- **Independent review of production code.** A fresh sub-agent gets the diff, the task description and the rules, but not the author's conclusions. In practice it found 1 to 9 critical bugs per session; critical remarks are fixed at once, the others go to the backlog.
