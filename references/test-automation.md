# Test automation: watching runs, series, sub-agents

Part of the `satisfactory-modding` skill. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

How to start the game for a test and the test mode itself: `references/testing.md`. The watcher scripts are `scripts/watch-run.sh` (results) and `scripts/behaviour-read.sh` (behaviour); the prompts for both are in `scripts/watcher-prompt.md`.

**Watching a series of automated runs while it goes**
- **Every run that lasts more than a few minutes gets two watchers, started together right after the run starts and stopped together (`TaskStop`) when it ends:** the result watcher (`scripts/watch-run.sh`) and the behaviour watcher (`scripts/behaviour-read.sh`), both on Haiku 5.5 at high effort (the owner's decision of 2026-10-29; from 2026-10-07 to then they ran on Sonnet at medium effort); the prompts for both are in `scripts/watcher-prompt.md`. The result watcher alone misses a mod that misbehaves with every check green. A session that pasted only the result prompt started no behaviour watcher until the user asked, and the Sonnet behaviour watcher then found two real mod bugs within minutes in each run. (2026-10-07, game 502094, SML 3.12.0, Sonnet 5.5)
- A packaged test run takes minutes (packaging 2–5 min, the game 1–20 min), so a series ties up the machine for an hour or more, and a broken run that is only read at its time limit wastes all of it.
  - While a run goes, check the game log every 30 s, not only at the end: the scenario's failure lines, the mod's warnings and errors, `Fatal error`, a crash report, and a run that has logged nothing new for a few minutes. Stop a run that has already failed instead of waiting for its time limit, and note at once when something done in the test window (a click, getting into a vehicle, a changed setting) disturbed it.
  - The watching can go to a sub-agent on a small model (Haiku 5.5 at high effort), not to the main model: it costs a few tool calls per run instead of the main session's context. The sub-agent runs a small shell script in a loop. The script reads only the log lines added since the last call, every 30 s, prints the first problem lines (deduplicated, without timestamps) or a "no new step for N s" line, then the number of lines it has read, and exits. The sub-agent sends what was printed verbatim to the main session (`SendMessage` to `main`), starts the script again from that line number, and stops after the result line. The main session reacts only to those messages. Start the first call from the current line count of the log (`wc -l < FactoryGame.log`) and its id (`head -n 1 FactoryGame.log | tr -dc '0-9.:-'`), not 0: until the new game start renames it, the log still holds the previous run, and from 0 the watcher reports that run's result as the new one. The script resets to 0 itself when the log shrinks. A run shorter than the 30 s step (a self-test that ends 25 s after the start, followed at once by the next run) can come and go between two reads, and the watcher then misses its result: the main session always reads the result line of the test script itself too.
  - Late reports of an earlier run (seen in practice: a watcher's hand-back arrived after the next run had started and read like news) are prevented three ways: (1) every report of the script starts with a line `RUN <test> started <time in the log>`, and the sub-agent passes it on unchanged, so the main session compares it with the run it started and drops anything older; (2) before it starts a new run, the main session stops the previous watcher (`TaskStop`), so nothing of it can arrive later; (3) the findings go only through `SendMessage`, and the sub-agent's final hand-back is the single word `done`, not a second copy of the result.
  - A watcher also ends itself: the script prints `GAME CLOSED, watch over` once the game process is gone and new log lines came since the last call (a closed or killed game, a run without a result), and the sub-agent stops on that line as on a result. While the run still packages and starts there is no game process yet; the script prints `game not started yet` then and the watcher keeps looping. The main session, for its part, stops the watcher (`TaskStop`) as soon as it has the result from the test script, whatever the watcher has said by then.
  - Evidence: a 20-minute run stood still for about 4 minutes because a station's setting was changed in the test window, and was noticed only when someone looked at the waiting train. (2026-10-04, game 502094, SML 3.12.0)
- **A second watcher looks at behaviour, not only at results.** The result watcher above reports failed checks, warnings and the result. A scenario can run for an hour with none of those while the mod misbehaves in a way a player would spot in a minute (seen on 2026-10-06: a move command re-issued every 10 s because the mod ended it a second after it began, with every check green). Next to the result watcher, run a second sub-agent on Haiku 5.5 at high effort (`scripts/behaviour-read.sh` is its reader, which waits 90 s and prints the mod's lines added since the last call) with a list of behavioural anomalies to report at once, with the evidence lines verbatim: the same command repeated for one object, an object standing still or in an error state for more than a minute while it has work, a task stuck in one state for more than ten minutes, a value flipping between two states every cycle, two objects claiming one place, a loaded object without a task (for a train mod: a train waiting at a signal, two trains at one station), plus the mod's warnings and the result line. Give it the shape of the status lines so it can read them, a list of what is normal (so it does not report design behaviour), a start time so it ignores the previous run's log, and a cap on iterations.
  - **`scripts/behaviour-read.sh` lost the start and the end of runs in a queue.** It started again from line 0 only when the log got shorter than `FROM`. In a queue each run starts a new game: when the new log was already longer than the old `FROM` at the next call, the script read it from that line on, so the first part of the new run never reached the behaviour watcher, and once the new game had renamed the old log, the old run's last lines, its `RESULT` among them, were never read. A watcher of an 8-run queue reported a run as silent with no result while the result watcher had its `RESULT` line, and four behaviour watchers reported a missing result line for runs whose copied log had `RESULT PASS`. The script now takes the log's id as a second argument and prints `LINES <n> <id>` as `watch-run.sh` does; when the id changes it prints the rest of the newest `FactoryGame-backup-*.log` first and reads the new log from line 0. (2026-10-12 and 2026-10-14, game 513885, SML 3.12.0)
  - **The first read of a new log can be too large for the behaviour watcher.** When the watcher's start values describe the previous log, its first call prints every `<MOD_LOG_CATEGORY>` line of the new log from line 0, including the mod's start-up self-test lines: about 100 KB in one project. The watcher (Haiku) got the output as a saved file, tried to read its tail and stopped there without reporting. `scripts/behaviour-read.sh` now prints at most the last `$MAX_LINES` (default 400) lines per call, with `... N earlier lines cut` before them; the self-test lines also go into `$DROP_PATTERN`. (2026-10-31, game 513885, watchers on Haiku 5.5)
  - The behaviour watcher's reader `scripts/behaviour-read.sh` prints `GAME CLOSED` whenever no game process runs, with no "new lines since the last call" condition (unlike `watch-run.sh`, see "The game is not running yet while the run packages and starts"). On a run that packages first, a behaviour watcher started together with the queue therefore reads `GAME CLOSED` during packaging and ends before the run's game is up. What works: start the result watcher with the queue as usual, but start the behaviour watcher only once the game process exists (a background `until tasklist | grep -qi FactoryGame; do sleep 5; done`), with FROM 0 and the id of the new log (its first line). Evidence: on a packaging run of `<scenario>` the behaviour watcher ended with `GAME CLOSED` while the mod packaged; on a later packaging run started that way it read the run from the first line of the new log until the result, with no early `GAME CLOSED`. (2026-10-17, game 513885, SML 3.12.0, watchers on Sonnet 5.5)
- **The watcher script is `scripts/watch-run.sh`** (bash, Git Bash on Windows), so no session has to write it again. Call it `bash watch-run.sh <test> <from_line> [<log_id>]`; the mod's log category and the prefix of the scenario's log lines come from the environment (`MOD_LOG_CATEGORY`, `TEST_TAG`; see the header of the script). It waits 30 s, reads the game log from the given line and prints `RUN <test> started <time>`, the new problem lines (failed checks, `RESULT`, the mod's warnings and errors, `Fatal error`), `no new step for 30 s`, and `LINES <n> <id>`; it resets to line 0 when the log shrank or its id changed (a new game start renames the old log). Evidence: Haiku sub-agents looping on it watched 9 runs of 2–20 minutes on 2026-10-05, reported failed checks and results, and stopped by themselves. Mistakes that cost runs that day, each fixed in the script or the prompt:
  - **The game is not running yet while the run packages and starts** (1–3 minutes). A first version printed `GAME CLOSED, watch over` then and the watcher stopped before the game came up. The script now prints it only when the game process is gone *and* new log lines came since the last call, and otherwise `game not started yet`, on which the watcher keeps looping.
  - **The start line has to be read, not guessed.** `wc -l < FactoryGame.log` right before the run starts; a number below the real length made the first call read the previous run's last lines, see no game and stop at once.
  - **Expected noise goes into `IGNORE_PATTERN`, not into the prompt.** With the mod's developer mode on, a self-test after every load logs a dozen deliberate `Rejected …` warnings. A Haiku watcher whose prompt listed them as expected still forwarded nine of them in two runs of two; `watch-run.sh` now takes `IGNORE_PATTERN` (extended regex) and drops matching problem lines itself, so the model only forwards what is printed. (2026-10-07, game 502094, SML 3.12.0, Haiku 4.5)
  - **`scripts/watch-run.sh` applies `IGNORE_PATTERN` to the `RESULT` line too** (`scripts/watch-run.sh`, line 43: `grep -Ev "$IGNORE_PATTERN"` runs over all problem lines, the result among them). When a word of the pattern also appears in the scenario's result text, the watcher never prints the `RESULT` line and reports only `GAME CLOSED, watch over`, although the log has the result just before the game closes. Seven runs of `<scenario>` in a row were reported that way: the watchers were started with `IGNORE_PATTERN='refused|Invalid aim|…'`, and the result read `<TEST_TAG> RESULT FAIL <scenario>: saved <save>, but 10 pieces were refused`. A watcher told to grep the log for the result after `GAME CLOSED` found it every time. What works: result words kept out of `IGNORE_PATTERN` (anchored to the step lines, e.g. `step hologram refused`), or a script that exempts lines matching the result prefix from the filter. Evidence: runs of 2026-10-25, each with `<TEST_TAG> RESULT FAIL … refused` in the copied log and `GAME CLOSED` without a result from the watcher; runs where the watcher's prompt asked for a grep after `GAME CLOSED` relayed the line. (2026-10-25, game 513885, SML 3.12.0, watchers on Sonnet 5.5)
  - **A new log is recognised by its first line, not only by its length.** One watcher missed a run's `RESULT` and kept watching the next game: comparing the line count with the last one does not tell the new log from the old one when the new log is already longer by the first read. The script takes a third argument, the first line of the log as last seen (`Log file open, <date> <time>` reduced to digits), prints it as `LINES <n> <id>`, and reads from line 0 when it changed.
  - **The watcher script met the moment without a log file.** The game renames its old log when it starts, so for a moment `FactoryGame.log` does not exist. `scripts/watch-run.sh` then printed the shell's own error (`…FactoryGame.log: No such file or directory`, from the `wc -l < "$LOG"` redirection, which fails before `2>/dev/null` applies) and `LINES 0` with no id, and the watching sub-agent forwarded that as a problem line. The script now checks for the file first and prints `game not started yet` with the caller's own `LINES <from> <id>`. Evidence: a watcher's message during a run's start, `line 23: …FactoryGame.log: No such file or directory`, `LINES 0`. (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)
  - **A watcher that counts every tagged line as progress misses a run that stands still.** A scenario that prints a status table every 30 s while it waits kept `watch-run.sh` quiet for 20 minutes although nothing happened (the train it waited for was switched out of the mod's control in that save). `watch-run.sh` now takes `STATUS_PATTERN`, an extended regex of such status lines; they no longer count as a new step. Also give every scenario its own short limit for "nothing started yet" (e.g. fail when no job was sent after 3 minutes) and let the watcher report "no new step" after about 2 minutes, not 5. Evidence: a 21-minute stall with only status lines in the log; the pattern left 0 progress lines of 32 in the stalled window. (2026-10-06, game 502094, SML 3.12.0)
  - **Two runs in one command** (a writer scenario, then the one that loads its save): a single watcher told to stop after the second `RESULT` did not stop and was still running 20 minutes later, sending stray shell errors into the conversation. One watcher per run instead, and the main session stops every watcher (`TaskStop`) as soon as it has the run's result from the test script, as above; the slip was not doing it.
  - **[?] A queue of runs needs one watcher per run, too.** A single Haiku watcher told to watch a five-run queue (one script that runs the scenarios one after another) and to stop after 5 `RESULT` lines kept going after the queue ended: one run had no `RESULT` (its game was closed by hand after a deadlock), so the watcher was one short, took the next game (a manual test with the user, which never prints steps) for a run and reported a false 3-minute stall. This is the "two runs in one command" slip again. For a queue, start a fresh watcher whenever the queue script prints its line for a finished run (e.g. `QUEUE 04 <scenario> exit 1`), or stop the watcher with `TaskStop` as soon as the queue prints its last line. Evidence: the false `STALL … (<scenario>)` came 12 minutes after `QUEUE done`. (2026-10-06, game 502094, SML 3.12.0, Haiku 4.5)
  - One result watcher (Sonnet, the prompt of `scripts/watcher-prompt.md`) can follow a queue of several runs when the prompt lists the test names in order and says to go on with the next name after each `RESULT` line and to treat `previous log:` as the previous run's result; six runs of 2 to 20 minutes were followed that way with one agent, no stray reports. The behaviour watcher stays one per run. (2026-10-11, game 502094, SML 3.12.0, Sonnet 5.5)
  - The two statements about a queue disagree and one of them needs a new test: the watcher that failed was Haiku and counted `RESULT` lines, the one below was Sonnet and was given the test names in order.
  - **[?] One result watcher on a queue names each result one run late.** `watch-run.sh` usually reads a run's `RESULT` as `previous log:` in the next run's log, so the watcher's report is headed with the next test's `RUN` line (`RUN <next test> … previous log: RESULT PASS <this test>`). The test name is on the `RESULT` line itself, not in the `RUN` header. Evidence: 18 reports of one Sonnet watcher on a queue, each headed with the following run. (2026-10-12, game 502094, SML 3.12.0)
  - A queue script with a `[string[]]` parameter started detached through `Start-Process powershell -File <script> -ArgumentList '-Only','02,03'` receives the one string `02,03`, and `'-Only','02','03'` binds only `02`: the script splits the value itself (`$Only = @($Only -split ',')`) and wraps the filtered list in `@()` (an `if` expression unwraps a one-element array, so `.Count` then counts the hashtable's keys). Evidence: a queue that printed `RUN 1/5` for a single filtered run, and one that ended with `QUEUE DONE` without starting a run. (2026-10-11, Windows PowerShell 5.1)
  - A queue script with a `[string[]]` parameter of run numbers called from another PowerShell script as `& script.ps1 -Only 07,08` receives the integers 7 and 8 (PowerShell parses unquoted numbers; the leading zero is lost), so `$_.N -in $Only` matches no run and the queue ends at once with `QUEUE DONE`; `-Only '07','08'` works. Evidence: a queue started with `-Only 07,08,11,12,21` ran only 11, 12 and 21 (`RUN 1/3 …`). (2026-10-11, Windows PowerShell 5.1)
  - **A watcher on a run that opens a new game read the run before as its own result.** The start values come from the old log; the new game renames it, so the first call saw another log id and printed `previous log: … RESULT …` of the earlier run, and Haiku watchers stopped on it a minute into a 40-minute run, also when the prompt said not to. `watch-run.sh` now prints `previous log:` only for result lines after the position the caller started from, so the run before is never reported; the prompt needs no rule about it. Evidence: a watcher's first message carried `previous log: <TEST_TAG> RESULT PASS <scenario of the run before>` and it ended with `done` at once. (2026-10-07, game 502094, SML 3.12.0, Haiku 4.5)
  - **Stop the old watchers before starting the new ones.** When a run ends, first `TaskStop` both of its watchers (a result watcher sometimes keeps looping when its first read landed in the previous game), then spawn the pair for the next run. In practice a watcher of one run was still alive while the next run already had its own pair.
  - **A run shorter than the watcher's first wait gets no watcher.** An autotest scenario that ends 23 s after the world loads was over, and its log renamed by the next run of the queue, before the watcher's first read; the watcher then sat on the next game for ten iterations ("still loading"). For such runs read the queue's `QUEUE NN <Test> exit <code>` line and the copied log instead, and start the next run's pair from the new log's id.
  - Prompt that worked (Haiku 4.5; from 2026-10-07 both watchers ran on Sonnet at medium effort, because Haiku 4.5 stopped on the wrong lines and forwarded listed noise; since 2026-10-29 they are Haiku 5.5 at high effort, a newer model than the 4.5 that failed, and the scripts now filter the lines): loop `bash watch-run.sh <test> <FROM> <ID>`, take `LINES n id` as the next FROM and ID, forward the output verbatim with `SendMessage` to `main` only when it holds a line other than `RUN`, `no new step`, `game not started yet`, `LINES` and the listed noise, stop after `RESULT` or `GAME CLOSED, watch over`, final answer the single word `done`. One of three watchers shortened what it forwarded: it sent only the `RESULT` line instead of the whole output with its `RUN <test> started` line, and ended with a sentence instead of `done`, so the main session could not tell which run the message belonged to. The prompt now says "send the WHOLE output of that call verbatim, every line including the `RUN` line" and "Your final answer is the single word `done`, nothing more." (2026-10-05, game 502094, SML 3.12.0, Haiku 4.5)
  - The prompt is now kept in `scripts/watcher-prompt.md`: fill in the placeholders and paste it unchanged. It also says to load SendMessage with ToolSearch when it is deferred, to run the script in the foreground and never to sleep, after a watcher told to sleep first armed a background wait and ended its turn. When the log's id changes, `watch-run.sh` now also prints the result lines of the newest backup log, prefixed `previous log:`. (2026-10-06, game 502094, SML 3.12.0)
  - **A watcher started while a run packages, right after a game was killed, can end at once with `GAME CLOSED`.** The killed game's log got three more lines after the start values were read (2717 then 2720); during packaging no game process runs, so `watch-run.sh` saw new lines and no game and printed `GAME CLOSED, watch over` before the run's game had started. Ways out, not tried yet **[?]**: count `GAME CLOSED` only for a log whose id is not the one passed at the start, or only after a line with the test tag has been seen in this log; or start the watcher once the run's game is up. Evidence: watcher output `RUN <scenario> started <time of the previous run>`, `no new step for 30 s`, `GAME CLOSED, watch over`, `LINES 2720 <old id>`. (2026-10-07, game 502094, SML 3.12.0, Sonnet 5.5)
  - **The result watcher's call cap has to follow the run's length.** A cap of 70 calls ended a watcher of an in-process reload scenario after 41 minutes (about 35 s a call: 30 s of the script's wait plus the agent's turn) while the run went on for over an hour; it answered `done` without a result. The cap in the prompt is now the run's timeout in seconds / 30, rounded up, and a watcher that stops on its cap sends `CAP REACHED, LINES <n> <id>` to main so a new one can take over. (2026-10-07, game 502094, SML 3.12.0, Sonnet 5.5)

- **Read a run's result lines from the game log, not from a console file.** A child PowerShell whose output went to a file (`Start-Process … *> file`) cut each long line about 55 characters after its prefix; the game log held the same 39 lines complete. (2026-10-03, game 502094, SML 3.12.0)
- A runner that marks a run CRASH when the game exits without a RESULT line marks a manual (player) scenario the same way when the user closes the game after testing by hand. For manual scenarios read the log instead: no `Assertion failed`, no new file in `.sentry-native\reports\`, and the scenario's own lines. (2026-10-21, game 513885, SML 3.12.0)
- **When the next game starts within seconds, the result is only in the backup log.** A run that ends with `RequestExit` and a queue that starts the next game at once leave `RESULT` and the summary lines in the renamed `FactoryGame-backup-<UTC>.log`; a watcher that stops when the log's first line changes must read the tail of the newest backup. Evidence: three watchers found their run's `RESULT` only in the backup log. (2026-10-06, game 502094, SML 3.12.0)
- **A server-and-client test pair: the server starts its scenario once a client's character exists and holds its result until the client has seen enough.** A test harness that quits the dedicated server with its result line drops the joined client at that moment, so a client-side check that needs time after the server's last event (here a train standing 20 s at its end) cannot give its own result. The server side waited for a controller with a pawn (`World->GetPlayerControllerIterator()`, `GetPawn()`, at most 300 s) before driving and gave its result 30 s after its last event (a core ticker with a 30 s delay); the client then watched the whole drive and passed 6 s before the server. Evidence: client `join 127.0.0.1:7777: joining` at 17:14:27, server drive started at 17:14:32, client `RESULT PASS <scenario>` at 17:17:11, server `RESULT PASS <scenario>` at 17:17:17. (2026-10-28, game and dedicated server 513885, SML 3.12.0)
