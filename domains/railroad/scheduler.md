# Railways: the native scheduler at path signals

Part of the `satisfactory-modding` skill, railroad domain (index: `domains/railroad/README.md`). Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. How the game orders trains that wait before the path signals of one junction, and how a mod can change that order. Hooks on the signalling itself are in `domains/railroad/signal-hooks.md`.

## The reservation queue

- **The native scheduler's queue at a path signal: `Priority = DependencyLevel × rollover + ReservationNumber % rollover`, at most one train newly approved per tick.** `AFGTrainScheduler::TickScheduler` runs once a frame, server only (`AFGRailroadSubsystem::Tick` with authority, after every train's `TickAtc`/`TickSelfDriving`/`TickPlayerDriving`), and calls `UpdateReservations`, `MakeNewReservations`, `UpdateDependencies`, `UpdatePrioritiesAndSort`, then `ApproveReservations`. `UpdatePrioritiesAndSort` gives `DependencyLevel` 0 to a train that depends on nobody (higher along a dependency chain, the train count in a cycle), sets `Priority = DependencyLevel * mReservationCounterRolloverAt + ReservationNumber % mReservationCounterRolloverAt` (rollover 100000) and value-sorts the private `mSchedulerInfos` ascending by `Priority` (unstable sort). `ApproveReservations` walks the map in that order, tries a train's last reservation first, and returns after the first train that got anything approved. Checked in the game with two trains waiting before path signals of one merge junction whose exit block was occupied by a third train: when that block came free, the train with the lower reservation number (both on level 0) was approved 1 frame later and the other about 11 s later, in 4 of 4 control runs. Evidence: `<scenario> result: <train A> into <junction> first (approved first <train A>, 1 frames after the block behind <exit signal> came free), <train B> second after 11.2 s; the game's own numbers <train A> 6 <train B> 8`. **[source]** Function order and formula read from `dumpbin /disasm` of the shipping DLL with its `.pdb` (`TickScheduler`, `UpdatePrioritiesAndSort`, `ApproveReservations`; `references/tools.md`). (2026-11-01, game 513885, SML 3.12.0)
- **A train gets its reservation number when its path reservation is created, that is when the path signal becomes its next signal; there is no distance threshold.** So the game's first-come order among trains waiting at one junction is the order in which their path signals became their next signals, not the order in which they set off or arrived. A train that set off 3 s after another got the earlier number (7 against 8): its path signal was its next signal straight from the station, 34 Foundations away, while the other's became next only behind an earlier junction. Evidence: `<train B>: res 1 … resno 7` at 272 m before its path signal, `<train A>: … resno 8`. **[source]** The number comes from `mReservationCounter` inside `MakeNewReservations` (`CreatePathReservation`, `CreatePathReservationFromInside`, `CreateExclusiveReservation`); only the path reservation from outside waits for `ApproveReservations`, the other two are approved at once. (2026-11-01, game 513885, SML 3.12.0)
- **A path signal's reservation chain also covers the block behind the junction's exit signal, and the game approves the last reservation of a chain first.** A train before a path signal holds a chain of two reservations, the path block of the junction and the block behind its exit signal. With a third train standing in the path block but the exit block free, the first train to create its chain got the exit block approved at once (`res 2 … last approved`), so the order was settled when the chains were created, not when the junction came free. In a test of the scheduler's order the block behind the junction's exit is the one that has to be occupied (the blocking train waits there), not the junction itself. (2026-11-01, game 513885, SML 3.12.0)

## Changing the order

- **The queue can be reordered without a hook by writing `FTrainSchedulerInfo::ReservationNumber`.** Through a `Friend` entry in AccessTransformers (`mSchedulerInfos` is private and not a `UPROPERTY`), a pass each frame on the server that rewrites every number the game has newly given to `rank * (rollover / 4) + native % (rollover / 4)` (rank 0 to 3) makes the game sort by `(DependencyLevel, rank, own number)`; the dependency level stays the first key, so trains are reordered only within one level and the approval tests that prevent deadlocks are untouched. In the two-trains-waiting set-up above, the train given rank 0 was approved first, 1 frame after the exit block came free, in 6 of 6 trials in which it had the later game number; both trains passed in every trial. Cost of the pass, including a check of `Priority == DependencyLevel * R + ReservationNumber % R` on every entry: average 4.76 µs, at most 68 µs a frame for 10 trains on a large save; 2.4–3.6 µs on average for 4 trains. Evidence: `<scenario> cost on 10 trains: avg 4.76 us (at most 20), max 68.00 us (at most 100), probe passed: within`. **[?]** A favoured train that reaches a free junction second cannot win this way: the first train's chain is approved in the frame it is created (read from `ApproveReservations`, not run). (2026-11-01, game 513885, SML 3.12.0)

## Giving way with a speed limit

- **Slowing down a train does not give up a path it holds: a train approved through a free junction keeps the path however slowly it drives, so lowering its speed to let another train through first makes the other one wait longer.** The game approves a path reservation when the path signal becomes the train's next signal and the junction is free (see "The reservation queue"); a speed limit written later (`mMaxVelocity` + `RecalculateConsistData`) changes nothing in the scheduler. With two trains 335 m from a merge, the one whose path signal was its next signal straight from its station (272 m) got the junction; limited to 40-50 km/h on its way to "yield", it held the path for longer and the other train stood 11-12 s at its own path signal (3 of 3 trials), against braking to 14.5 km/h without the limit. The same on a passing loop: the train coming off the loop, its merge path signal its next signal on the loop, held the merge while the train on the main line stood 16.5-18.1 s (2 of 2). A train still a block or more before the junction's path signal can be slowed so that it asks later (3 of 3 at a merge where it did, the other train never below 54 km/h). So a speed limit can only give way at a junction before the junction's path signal becomes the train's next signal. Evidence: the mod's line limiting `<train>` to 40 km/h to give way to `<other>` at the junction, then `<other>: 0 km/h … waiting at signal 11 s, next restrictive signal <path signal> (RSA_Stop, 10 m ahead)` with `<train>` at 104 km/h past it. (2026-11-02, game 513885, SML 3.12.0)

## Reading a path signal's blocks

- **`GetObservedConnections()` of a path signal gives the path block behind it, `GetGuardedConnections()` the block before it**, the same as for a block signal (`domains/railroad/signals.md`, "A signal between two tracks"): taking the junction's block from the guarded side gave the plain block before the path signal. Evidence: `blocks at <junction>'s signals: <path signal> observed path, <exit signal> guarded path, <path signal> guarded plain, <exit signal> observed plain`. (2026-11-01, game 513885, SML 3.12.0)
