# Railways: notes on game classes, moved from the core

Part of the `satisfactory-modding` skill, railroad domain (index: `domains/railroad/README.md`). Railway facts that sat in the core files `game-classes.md`, `game-systems.md`, `multiplayer.md` and `ui.md`, moved here verbatim; each core file keeps one pointer line. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain. Replace the parts in `<...>` with your own.

## From game-classes.md (Buildings: actors and lightweight)

- **`AFGBuildableSubsystem::mBuildableRemovedDelegate` fires for buildables dismantled from code and can drive a cache of railway pieces.** A `UObject` bound with `AddUniqueDynamic` to `mBuildableAddedDelegate` and `mBuildableRemovedDelegate` (both `FOnBuildableAdded`-style dynamic multicast delegates with one `AFGBuildable*` parameter) got one call for each of four signals and one track dismantled with `IFGDismantleInterface::Execute_Dismantle`; a once-a-second comparison of all tracks, signals and stations found no change the delegates had not announced.
  - When bound in the first tick of a loaded world, the added delegate still fired for the save's train platforms (30 calls on a save with 11 stations) but not for its 142 tracks and 68 signals, so a first full read is needed anyway. Both delegates also fire for what the player does by hand: four tracks built, one dismantled, and a signal placed in the middle of a rail (the 48.00 m track actor is removed and two new ones of 32.39 m and 15.61 m appear, each announced). Stations built and dismantled by the player while the game runs are announced the same way (5 → 6 → 7 → 8 stations, then 8 → 6; 182 build events in one manual session). Not seen yet: a blueprint with tracks, and dismantling many buildings at once.
  - Evidence: `13 build events so far, 0 changes without one` after the dismantling; `30 changes so far, 0 without a build event` at the first read; `0 changes without a build event so far` after each of six graphs rebuilt during the player's building. (2026-10-05, game 502094, SML 3.12.0)

- **Listing one buildable class on a big save: `TActorIterator` over the world took 1.16 ms in one frame; `GetAllBuildablesRef()` can be read a part a frame.** A save with 1830 railway tracks among tens of thousands of actors: `TActorIterator<AFGBuildableRailroadTrack>` took 1.16 ms on the first load (0.4 ms on later loads in the same process). Walking `AFGBuildableSubsystem::GetAllBuildablesRef()` with a cursor, a `Cast` per entry and a budget check every 256 entries spread the same work over frames, longest frame 0.81 ms for the whole multi-stage task. A build event during the walk can move the list, so restart the walk when one comes. Evidence: `last read 4.51 ms in 73 frames, 1.161 ms in its longest frame` before, `read in 6.127 ms over 99 frames, the longest 0.814 ms` after, same track count. (2026-10-13, game 502094)

## From game-systems.md

- **A build-gun hologram snaps only to the actor the hit is on.** Moving `Hit.Location`/`ImpactPoint` of a floor hit onto a free track end (or next to a station) and calling `UpdateHologramPlacement(hit)` places the hologram there, but the track hologram does not connect to that end and a platform hologram does not attach to the station (`FGCDMustAttachToTrainPlatform` "This must be placed inline with another train platform!"). A synthetic hit whose actor and component are the target works: `FHitResult(<track>, <its primitive component>, <connector location>, FVector::UpVector)` with `bBlockingHit = true` (or the station actor for a platform). Evidence: <scenario>, before: every new track built but `a:[] b:[]` (no connection) in the layout dump; after: all tracks joined to the station's end and to each other, the platform on the station. (2026-10-25, game 513885, SML 3.12.0)

- **Dismantling a station from code leaves its track behind.** `IFGDismantleInterface::Execute_Dismantle(<station>)` removes the building but not its integrated track (`Build_RailroadTrackIntegrated_C`); a station built again at the same spot then stood on that leftover track, 1.36 m higher, and the line built next attached to the leftover track. The dismantle gun removes the children first, and the same works from code: `Execute_GetChildDismantleActors(<station>, children)`, `Execute_Dismantle` on each, then on the station (`dismantled with 1 children`). Evidence: <scenario>, a track snapped to `Build_RailroadTrackIntegrated_C_<id>` of the dismantled station, the dump showing the new station unconnected. (2026-10-25, game 513885, SML 3.12.0)

## From multiplayer.md

- On a client, `AFGRailroadSubsystem`'s station list has null entries in the first seconds after joining (identifiers not replicated yet), and train consists may be empty while the locomotive actors already exist. Guard with `IsValid` and find locomotives with `TActorIterator<AFGLocomotive>`. Evidence: client crash `EXCEPTION_ACCESS_VIOLATION` in `AFGTrainStationIdentifier::GetStationName` from a loop over the list. (2026-10-21, game 513885)

- A mod subsystem with `ESubsystemReplicationPolicy::SpawnOnServer_Replicate`, `bAlwaysRelevant = true` and `UPROPERTY(SaveGame, ReplicatedUsing = OnRep_X)` arrays (a `TArray` of a `USTRUCT` holding `TObjectPtr` to station identifiers and `TSubclassOf` items, a `TArray<TObjectPtr<AFGTrain>>`, a `TArray<TObjectPtr<AFGBuildableRailroadSignal>>`) reaches a client of a dedicated server with the values loaded from the save, and again after every server load; `BeginPlay` runs on the client too, so server-only work goes behind `if (!HasAuthority()) { ...; return; }`, and the initial replicated values are already set in the client's `BeginPlay`. Changes made on the server through a remote call object came back to the client within 0.5 s at `SetNetUpdateFrequency(4.f)`. Evidence: client log line "Subsystem on a client: 4 stations, 3 parking signals, 0 trains out of the pool" at BeginPlay, and four client worlds with server-side changes seen on the client. (2026-10-22, game 513885, SML 3.12.0)

## From ui.md

- Where the game shows a train's self-driving warning (`SDLE_NoTimeTable` and other `ESelfDrivingLocomotiveError` values), so a mod can replace the look without native hooks: (1) the cab HUD bar is `Widget_TrainWarning_C` inside `Widget_Locomotive_HUD_C` (`/Game/FactoryGame/Buildable/Vehicle/Train/Locomotive/UI/Widget_TrainWarning`), its `UpdateWarning` reads `GetSelfDrivingError`; inner widgets `mWarning`, `mWarningText`, `mWarningIcon`, background `Image_0` whose brush carries a red tint (a `SetColorAndOpacity` alone multiplies with it; `SetBrushTintColor(White)` removes the tint); (2) the locomotive window's Status part is `BPW_LocomotiveStatus_C` (`mIcon`, `mTextObject`, `mTrain`, `SetTrainStatus`), the same class in the map's train details (`BPW_ActorDetails_Train_C`); (3) the map icon is `Widget_MapCompass_Icon_C` in `Widget_MapObject_C` (`mActorRepresentation`, `mMapIconMaterial`, image `mMapIconNEW`, event `OnTrainStateChanged(ETrainStatus)`); (4) the compass is drawn by Slate from `AFGHUD::GetCompassEntries()`, not from widgets: each `FCompassEntry` has `RepresentingActor` and a `Brush` whose resource is a MID of `MI_CompassIcon_Moving_Train` (parent `MM_UI_CompassIcon`), so a paint holds only when it is made before Slate's tick (`FSlateApplication::OnPreTick`); `UFGActorRepresentation::UpdateRepresentationCompassMaterial(MID, PC)` makes the game set its own values again.
  - The game's loading spinner textures are `/Game/FactoryGame/Interface/UI/Loading/SpinnerForeground` and `SpinnerBackground`. Evidence: widget tree and parameter dumps in the packaged game, a mod replacing all four for <train> on <scenario> (screenshots, checks PASS). (2026-11-17, game 517554, SML 3.12.0)

- The compass and map icon material (`MM_UI_CompassIcon`, the same MID kind on the compass and the map) composes a train icon like this: the `Border` texture's alpha is the icon's whole shape; inside it a circle of `ColorPrimary` reaches about 0.34 of the quad (scaled with `InnerBackgroundScale`, default 0.68, texture `InnerBackground` = `Circle_Background`); the `Icon` texture is drawn on it in `ColorSecondary`; the rest of the alpha shows the `Border` texture's RGB × `BorderColor`. `UsesBorder=0` drops the circle and leaves only the pictogram. `BorderRotation` (0..1 of a turn) turns the `Border` texture, and a growing value turns it counter-clockwise on screen. A game train defaults: `Border`=`MapCompass_Circle_Border`, `BorderColor` white, `ColorPrimary` 0.05 grey, `ColorSecondary` white or the warning orange, `IsBlinking` 1 on a warning. A loading arc around the circle therefore needs a `Border` texture with an opaque disc inside and the arc outside 0.34 (a transient `UTexture2D::CreateTransient` B8G8R8A8 works); the game's `SpinnerForeground` as `Border` hides the circle and the pictogram. Evidence: probes setting R, G, B, A and filled variants of a transient `Border` with distinct colours, screenshots; a held texture turned to a quarter turn showed its gap 90° counter-clockwise. (2026-11-17, game 517554, SML 3.12.0)
