# Railways: how signals are placed and what the game checks

Part of the `satisfactory-modding` skill, railroad domain (index: `domains/railroad/README.md`). Split from `domains/railroad/signals.md`, which holds the signals and track connections. Markers: no marker = verified in practice, **[source]** = read from SML or game code, not tested, **[?]** = uncertain.

## How signals are placed and what the game checks

Rules for build lists, test layouts and layout checks. Collected from the game headers, the wiki and the signal guide hosted on the modding docs; the items with evidence were also read from a built layout with 22 signals, all `RBV_Valid`.

- **A signal is directional. One signal at a joint makes the joint one-way; a two-way track needs a pair at the same joint, one per direction.** In code: a signal that has a partner at its joint returns `IsBiDirectional() == true` and each of the two connections has one signal as `GetFacingSignal()` and the other as `GetTrailingSignal()`. A lone signal returns false, and the connection behind it has only a trailing signal, so nothing may pass it from that side. Evidence: `signal S07 block …, two-way 0, guards [T14.0]`, `T15.1 trailing S07`; `signal S13 block …, two-way 1`, `T18.0 facing S13 trailing S14`. Wiki: "If only one signal is present, it will prevent trains in the opposite direction from passing through." (https://satisfactory.wiki.gg/wiki/Train_Signals)
- **A signal placed at a switch sits on the switch's point and covers both branches**: it guards or observes two connections. Evidence: `signal S08 block …, guards [T14.1 T16.0], observes [T10.1]` and its partner `signal S21 path …, guards [T10.1], observes [T14.1 T16.0], observed block 4 (path block)`.
- **A block entered through path signals is a path block**: `FFGRailroadSignalBlock::IsPathBlock()` was true for exactly the blocks whose entry signals were path signals. **[source]** All entry signals of a block must be of one kind, exit signals may differ (wiki).
- **[source]** The block validation errors, enum `ERailroadBlockValidation` in `FGRailroadSignalBlock.h`, with the text the player sees (wiki): `RBV_NoExitSignals` "Block has no exit signal", `RBV_ContainsLoop` "Signal loops into itself" (the signal does not divide anything, also when two unconnected tracks lie too close: **[source]** the headers (`RAILROAD_BLOCK_OVERLAP_DISTANCE = 600.f`, cm, `Buildables/FGBuildableRailroadTrack.h:371`) and a tutorial give 6 m, confirmed by the 5 m / 6 m measurement above; the docs signal guide advises keeping parallel tracks about 1.5 Foundations (about 12 m) apart, which is a safety margin above the 6 m threshold; unconnected parallel tracks 6, 7, 8, 12, 16 and 24 m apart had separate blocks, 5 m apart `RBV_ContainsLoop`: `<scenario> SIGNAL ... RBV_Valid, ... nearest unconnected track 6.00 m away, block -1 (-)` (2026-10-26, game 513885, SML 3.12.0)), `RBV_ContainsMixedEntrySignals` "Block has conflicting entry signal types", `RBV_ContainsStation` "Path block cannot contain stations". A signal at the very end of a track has no valid connections ("Signal has missing connections", `HasValidConnections()` false). A signal with an error counts as red.
- **[source]** A path signal is red until an approaching train has its path reserved; the reservation runs through every following path signal up to the next block signal, and the block behind that signal must be free ("trains will only enter a Path Segment if the following Block Segment is clear", signal guide on docs.ficsit.app). A train does not stop inside a path block. So: path signal on every entrance of a junction, block signal on every exit, and no path signal directly before a station (the station would be inside the path block). Players also put block signals on the stretches between junctions, so more than one train fits on a line: a layout built that way by a player had 22 signals, all valid, and two shuttle trains ran 5 courses each without an error (2026-10-04, game 502094, SML 3.12.0). Claims of the wiki and the community signal guide, read through a summary, tested (2026-10-26, game 513885, SML 3.12.0): a train driven from the cab occupies its block, and a path signal ahead stays `RSA_Stop` for it (the game does not stop a driven train; it ran past the red signal: `<scenario> POSSESS t=17.6 ... own block 0 occupied 1 by it 1, path signal RSA_Stop -22.2 m ahead`). Wrong: a light train (locomotive and two empty Freight Cars) at 120 km/h began braking for a red block signal 152 m ahead, not about 250 m (`braking for <signal> began 152 m before it, from 33.1 m/s`; heavier trains not measured); signals 1 m and 4 m from a free track end have valid connections (`connections guarded 1 observed 1 (valid 1)`), so the signal logic has no 12 m minimum (**[?]** whether the signal hologram refuses such spots was not tried). **[?]** Not tested: a path block should be level or trains may collide (needs an over-crossing inside one path block). Advice, not a game rule: block spacing of 3–4 track lengths at most (wiki) or about 1.5 train lengths (guide); blocks of any length worked. The side of the track a signal stands on (wiki: Left Side/Right Side build modes since 1.1) does not matter for trains: docs.ficsit.app says "trains only look for signals on the right-hand side", which a test disproved (entry below); in the headers handedness only picks the mesh and transform (`mRightHandedMesh`/`mLeftHandedMesh` with their transforms, `Buildables/FGBuildableRailroadSignal.h:19-29`; `IsLeftHanded()` :110-112; `mIsLeftHanded` :291-293; hologram build mode `mBuildModeLeftHanded`, `Hologram/FGRailroadSignalHologram.h:63`), and the logic binds a signal to track connections as facing/guarded and trailing/observed (`FGBuildableRailroadSignal.h:215-235`). So the docs claim is outdated (older left/right build modes) **[source]**. Docs agree with the **[source]** text above on: no path signal directly before a station (`RBV_ContainsStation`, `FGRailroadSignalBlock.h:19`) and chained path signals reaching the next block signal. (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **[source]** The game's pathfinding ignores other trains and takes the shortest route, so two two-way tracks side by side are no passing loop: both directions pick the same one. A passing loop needs each of its two tracks made one-way, with a single block signal behind the switch where a train enters the loop track and a single path signal before the switch where it leaves it (Steam discussion 6982351509012486495; the built layout above is signalled this way). The docs signal guide says the same ("a pass around", the shortest path decides). (2026-10-24, game 513885, SML 3.12.0, docs.ficsit.app)
- **The signal's side does not change its logic (the docs' "trains only look for signals on the right-hand side" is wrong).** A Block Signal and a Path Signal built Left Side behave like Right Side ones at the same spot: on a one-way loop a train held by a train in the block behind stopped with its front 2.00 m before the signal (`RSA_Stop`) and moved 6.1 s (block) and 1.5 s (path) after it turned `RSA_Clear`, the same on both saves, 2 runs each; `RBV_Valid`, 0 invalid signals. The side only shows in `IsLeftHanded()`. Evidence: `<scenario> stop A front 2.00 m before it, aspect RSA_Stop, left-handed 1` against the same line with `left-handed 0`. (2026-10-25, game 513885, SML 3.12.0) The same holds at switches and in a two-way pair: a loop with its six switch and siding signals built Left Side ran two trains 600 s with the same 18/18 arrivals and 0 invalid signals as the all Right Side save (`<scenario> layout: 0 signals not valid, 13 non-path blocks; route ... signals: path L , block L , block R , ...`), and a two-way stretch with Left Side entry signals and Right Side opposite numbers ran two push-pull trains 14 stops each, never both in one block. (2026-10-26, game 513885, SML 3.12.0)
- **A partly signalled network works; "signals are all or nothing" (community signal guide) is advice, not a game rule.** A one-way loop with a passing siding and four stations, once with all 13 signals and once with only the 7 of one straight (the other straight with both switches, the siding and its station one block): two trains on the game's timetables, 600 s, 2 runs each: 0 invalid signals, `SDLE_NoError`, no deadlock, never both trains in one non-path block. The only cost was capacity: one train arrived 14 times instead of 18. Evidence: `<scenario> t=600 arrivals A-train 14 D-train 21, … both in one block 0 times 0.0 s, errors SDLE_NoError / SDLE_NoError` (7 signals) against `18 / 18` (13 signals). The waiting counter read 0 s because the trains waited docked at stations. (2026-10-25, game 513885, SML 3.12.0)
  - The 21 arrivals are real, not a stop counted twice: counted once per station change, the D-train calls at three stations per lap and the A-train at two, both laps about 90 s. The same loop with no signals at all ran two trains 600 s, 18/18, no error (`<scenario> t=600 arrivals A-train 18 D-train 18 (once per station: 18 / 18), ... errors SDLE_NoError / SDLE_NoError`); those trains never caught up with each other, so this does not show that an unsignalled network protects trains that meet. A two-way stretch and its end station left undivided worked (`domains/railroad/push-pull-lines.md`). A signalled area ending in a Buffer Stop with no signal in front of it does not work: its last block signal reports `RBV_NoExitSignals` and stops every train; one more block signal facing the Buffer Stop fixed it (the dead-end entry below). (2026-10-26, game 513885, SML 3.12.0)
- **[source]** The modding docs have no page on the signal classes; their only railway text is the community signal guide (https://docs.ficsit.app/satisfactory-modding/latest/CommunityResources/TrainSignalGuide.html). The FicsIt-Networks reflection pages list `RailroadSignal` and `RailroadSignalBlock`. (2026-10-03, game 502094, SML 3.12.0)
- A signal deep in a dead-end siding, facing the train that drives in, needs a second signal between it and the Buffer Stop or the game marks it `RBV_NoExitSignals` ("Block has no exit signal") and shows `RSA_Stop`: the stub it observes has no exit. With the second signal at the Buffer Stop the inner signal is `RBV_Valid` and the second one carries the error instead. A train whose route ends at the inner signal stops there either way (the route's end, not the aspect, stops it). This answers the **[?]** in `domains/railroad/own-routes.md` ("Whether the parking signal would be valid without it was not tried"): it is not. Evidence: dismantling the Buffer Stop signal from code turned the inner signal from `RBV_Valid` to `RBV_NoExitSignals, aspect RSA_Stop` within 5 s (packaged game, 2026-10-11, game 502094, SML 3.12.0).
- On a two-way line with a passing loop (two one-way tracks) and an end station, making the stretch from the loop's far switch to the station one block (every signal between them dismantled, the loop's own signals kept) does not prevent the head-on deadlock of two trains: the train bound for the occupied station waits at the loop's exit signal with its front on the switch, and the train leaving the station cannot enter the other loop track. Where the waiting train stops decides, not the number of blocks. Evidence: both trains stood for over 220 s at signals 10 m ahead of them (`waiting at signal 262 s` and `223 s` in the status lines); with the signals as built they stood 261 s and 240 s the same way. (2026-10-11, game 502094, SML 3.12.0)
- A train on a siding under a Path Signal whose way out leads through a junction to an occupied station track waits at the Path Signal (`RSA_Stop`). It moves 1–2 s after the station track is free. The mod needs no action of its own to leave the siding just in time. Evidence: <scenario>: `waits under the path signal while <station> behind the junction is taken: moved 0, path signal RSA_Stop, waiting at signal 21 s`, then `track free at 6.5 s, moved at 8.0 s of the stage`. (2026-10-12, game 502094, SML 3.12.0)
- **A signal at the very joint of a switch guards or observes more than one connection.** A siding's exit signal placed exactly where the siding joins the line (the merge) has `GetGuardedConnections()` of 2 (the end of the siding and the end of the line's track) and `GetObservedConnections()` of 1 (the track after the merge, whose connection has 2 connections). A signal placed where the tracks part (before the split) has 1 guarded and 2 observed. On a layout built the way players build (a Path Signal on the line before the split, block signals at the merge), the siding and the line beside it are then one Path Signal block from the split to the merge, so a "siding is a block of its own" rule refuses every such siding. Evidence: 52 signals of <test layout>: 8 with 1 guarded / 2 observed at splits, 7 with 2 guarded at merges, all 7 refused as "1 other track(s) in the block". A train standing on the siding branch at the switch does not let another train through the line branch (next two entries). (2026-10-13, game 502094, SML 3.12.0)
- A train standing still inside a path block keeps every train whose path through that block overlaps the tracks it stands on, and the game counts the two tracks that converge into a switch as overlapping. Case: a siding whose exit signal stands at the switch where it joins the line, with a Path Signal before that switch on the siding and on the line, so the stubs of both before the switch are one path block. A train parked 8 m before the exit signal (its route ends there) stood on the siding's last track, and `GetOverlappingTracks()` of that track named the line's last track. Another train then stood at the Path Signal into the block on the line for 180 s (`next restrictive <path signal> RSA_Stop`, test stopped); with the parked train away, the same train drove the same way through the block in 7.4 s without a wait. So a parking place must not be inside a path block that the line beside it also uses near a switch; the header comment of `FFGRailroadSignalBlock` says the same in words ("If a train is parked inside a path block other trains cannot reserve a path that intersects with the parked train"). So a train parked on the siding branch at the switch does not let another train through the line branch. Evidence: `<scenario>`, kind "merge": `control done, A away: B is through the block 7.4 s after it began … stood at the signals into the shared block 0.0 s`, `A's vehicles stand on 1 tracks … tracks of the line the game counts as overlapping them: 1`, `B stood 180 s at <path signal> into it`. The earlier try waited 417 s at the same signal but had no run without the parked train to compare with. (2026-10-14, game 513885, SML 3.12.0)
- The same holds where the line splits: a siding with no entry signal of its own leaves the line at a switch inside a path block, its exit (parking) signal at the far end of its first track. A train parked 8 m before that exit signal stood on the siding's first track after the switch, which the game counts as overlapping the line's first track after the switch (`GetOverlappingTracks()`: 1). Another train going along the line through the block stood 180 s at the Path Signal into it; with the parked train away it drove through in 15.7 s without a wait. So a siding that shares a path block with the line, on either side of a switch, is not a parking place when the parked train stands on a track next to the switch. Not tried: a siding long enough that the parked train stands only on tracks no line track overlaps. Evidence: `<scenario>`, kind "split": `control done, A away: B is through the block 15.7 s after it began`, `A's vehicles stand on 1 tracks, all on the siding branch 1, on the line or the shared track 0; tracks of the line the game counts as overlapping them: 1`, `B stood 180 s at <path signal> into it`. (2026-10-14, game 513885, SML 3.12.0)
